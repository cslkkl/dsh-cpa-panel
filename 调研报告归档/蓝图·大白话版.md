## 压缩结论（先看这一段）

在你自己那台 Windows 电脑上，**只装一个 DSH 插件**，它会帮你把"转发 AI 请求 + 自动养号"整套东西全部拉起来、配好、看住。你不用装 Docker、不用手动配后端、也不会看到第二个网页界面——**唯一的界面就是这个插件在 DSH 里的配置页/状态页**。

系统由三个现成的开源项目改造而来，分工一句话：
- **一个主服务程序（exe）**：负责把 AI 请求转发到各渠道账号，顺手做养号；**只裁剪、不重写**。
- **几个渠道小插件（dll）**：每个渠道一个，里面装着该渠道的登录、签到、领奖规则；按养号能力保留 WorkBuddy / Qoder / Trae，砍掉没用的 Mimo。
- **DSH 插件（唯一界面）**：负责首启自动下载、自动配置、拉起并看住上面那个 exe，给你一个能看余额、能开关养号、能管理"调用单元"的页面。

核心新规矩：**每一个"渠道 × 账号 × 模型"组合 = 一个独立单元，每个单元一把独立钥匙**，调用时绝不用错账号、绝不自动轮换。最后有 **6 件事需要你拍板**。

## 1. 最终系统：一段话讲清 + 一张图

**一段话：** 你在 DSH 里启用这个插件后，它会自动把一个叫"主服务"的小程序在你电脑后台跑起来，并接好几个"渠道小插件"。你之后从任何地方发的 AI 请求，都会经这个主服务转发到你指定的那个渠道账号上；同时，这个插件会**自动帮你登录的那些账号每天签到、做任务、领奖励、保持在线**，让账号持续有钱、不会被踢下线。你能看到的一切，都在这个 DSH 插件页里完成——没有第二个后台、没有命令行、没有手动配文件。

> 名词垫一句：**DSH（DeepSeek Harness）**就是你现在用的这个工作台程序；**插件**是装进 DSH 的一个扩展；**exe / dll** 都是 Windows 里的小程序/小模块，区别是 exe 自己独立跑、dll 得被 exe 外挂着跑。

```
┌──────────────────────────────────────────────────────────────┐
│  ① 你在 DSH 里看到的页面（全系统唯一的界面）                    │
│     看账号余额 / 今天签没签到 / 开关养号 / 管理"调用单元"        │
└───────────────┬────────────────────────────────────────────┘
                │ 网页只跟下面这个插件的"后台半边"说话
                │ （网页永远拿不到管理密码，安全）
                ▼
┌──────────────────────────────────────────────────────────────┐
│  ② DSH 插件（装在 DSH 里，唯一界面的主人）                      │
│     · 第一次启用：自动下载主服务和渠道插件、自动写好配置、        │
│       自动生成随机管理密码、自动把主服务拉起来                   │
│     · 平时：看住主服务进程（崩了自动拉回）、管单元列表和养号开关  │
└───────┬──────────────────────────────────────────────────────┘
        │ 本机内通话（只认本机 127.0.0.1，外网够不着）
        │ 一路发 AI 请求，一路收状态/余额
        ▼
┌──────────────────────────────────────────────────────────────┐
│  ③ 主服务 exe（一个独立的 Go 程序，真正干活的转发中枢）          │
│     · 把 AI 请求按"单元"钉死账号转发出去                        │
│     · 管账号、管签到/做任务/领奖的定时调度                      │
└───────┬──────────────────────────────────────────────────────┘
        │ C 语言接口（人话：同一个进程里直接互相调用，快）
        ▼
┌──────────────────────────────────────────────────────────────┐
│  ④ 渠道插件 dll（每个渠道外挂一个小模块）                       │
│     workbuddy.dll / qoder.dll / trae.dll …（zcode 待定）        │
│     · 每个渠道怎么登录、怎么签名、怎么签到领奖，全写死在里面      │
└───────┬──────────────────────────────────────────────────────┘
        │ 加密联网（HTTPS）
        ▼
        各渠道官方服务器
        WorkBuddy · Qoder · Trae ·（ZCode 可选）
```

> 关键安全设计：**管理密码只在第②层（插件后台半边）手里**，网页（第①层）永远拿不到；主服务只监听本机回环地址，外面网络摸不到。

## 2. 三个主仓库最终变成什么、怎么配合、为什么这么分工

| 仓库 | 改造后是什么 | 在系统里的角色 |
|---|---|---|
| **① CLIProxyAPI**（Go 主服务，出 exe） | 一个"瘦身版"转发中枢：只留转发核心 + 养号定时调度 + 账号管理接口；删掉自带网页、Docker 和一堆用不到的功能 | 图中第③层。**真正转发 AI 请求的手**，同时管账号和养号节奏 |
| **② cpa-multi-plugins**（Go 插件集，出 dll） | 按养号能力保留：WorkBuddy（最全：签到/任务/领奖/保活全有）、Qoder（签到 + 领 Pro + 保活）、Trae（仅签到）；ZCode 可选；Mimo 删掉 | 图中第④层。**每个渠道的"方言翻译官"**，把各渠道五花八门的登录/签名/签到规则封装好 |
| **③ dsh-cpa-panel**（DSH 插件） | 从手写 JS 改成 TypeScript（照一个成熟范本的工程写法）；它的配置页/状态页就是全系统唯一界面；负责首启自动配置、托管主服务进程、管单元列表和养号开关 | 图中第①②层。**你能摸到的全部**，也是背后那个"保姆" |

**三者怎么咬合成一件事：**
DSH 插件（③）第一次启用时，去下载主服务 exe（①）和几个渠道 dll（②），写好配置，把 exe 拉起来；之后你在插件页里的每一个动作（看余额、开关签到、启停账号），都是插件后台半边去指挥主服务，主服务再通过 C 接口喊对应渠道 dll 去和渠道官网打交道。**加一个渠道 = 往 plugins 文件夹放一个 dll，主服务代码一行不用动**——这是这套架构天生的好处。

**为什么这么分工：** 把"你能看到的界面"（③）、"转发调度的中枢"（①）、"各渠道脏活累活"（②）彻底分开。界面随便改、渠道随便加删，互不牵动。

## 3. 保留 vs 砍掉清单（人话逐项）

### ✅ 保留（这些是吃饭的家伙）

- **转发核心、账号管理、配置热加载**：发 AI 请求、增删启停账号、改配置不用重启——这是主服务的命根子。
- **插件外挂机制**：能像插 U 盘一样挂 dll，加渠道零改动。
- **WorkBuddy 的全套养号**：签到、做任务、领奖、**保活**（定时刷登录态，不做会被上游批量踢下线）、定时调度。它是养号能力最全的渠道。
- **Qoder**：签到 + 领 Pro 升级包 + 保活；**Trae（国内版）**：每日签到。
- **两套密码体系**：一把"管理密码"指挥后台、一把"访问钥匙"接收 AI 请求，互不串。
- **健康检查、优雅停机、进程托管**：主服务起没起好、崩了怎么办、关的时候不留烂摊子。

### ✂️ 砍掉（砍了不影响跑，反而更轻更安全）

- **Docker 全套**（Dockerfile、compose 等）。**为什么砍**：我们只在你这一台 Windows 上跑，不需要"集装箱"那套。**影响**：无，反而少一层。
- **主服务自带的网页后台**（management.html、插件自带面板页、启动时自动开浏览器）。**为什么砍**：全系统唯一界面就是 DSH 插件页，后端只回数据不画图。**影响**：你以后不会再被引导去一个旧网页；账号导入得换个方式（见第 6 节拍板项④）。
- **一堆用不到的后端模块**：终端交互界面、实时通话（WebRTC）、首页控制台、数据库（Postgres）、局域网设备发现、内置的一堆厂商登录、远程模型自动更新。**为什么砍**：单机、单用户、只用这几个渠道，全用不上。**影响**：exe 更小、启动更快、暴露的攻击面更小。
- **旧接口里约 90 条配置读写**。**为什么砍**：有更新的一套接口够用，旧的留着只是攻击面。**影响**：无。
- **Mimo 渠道**。**为什么砍**：它签到/领奖/任务/保活一样都没有，养号价值为零。**影响**：除非你专门想用 Mimo 转发，否则无感。
- **面板里的花活**：拖拽排序、跨渠道余额汇总条、额度进度条。**为什么砍**：余额本来就逐行显示，单位还不一样，汇总没意义。**影响**：页面更干净。

## 4. 为什么这么改（四个"为什么"）

**① 后端为什么"只裁剪、不重写"？**
因为这个主服务被 **906 个自动测试文件**死死守着（它自己 761 个 + 插件 145 个），而且"要删的赘肉"和"要留的核心"在目录上早就分开了——删赘肉就是删文件夹，动不到核心。一旦重写，等于一次性扔掉这 906 个测试的保护，还得重新去踩各渠道协议（签名、数据格式）的坑。**重写在性能上也没有任何收益**（它的转发模型本来就是对的）。所以：删赘肉、打几个小补丁，绝不推倒重来。

**② 插件为什么要从 JS 改成 TypeScript？**
现在这个面板插件是"手写野路子"：没有构建脚本、没有任何自动测试、网页端是手工拼出来的——能跑，但没有护栏。而隔壁已经有一个写得很规范的 DSH 插件范本（TS 版），直接照它的工程模板套，就白捡了"类型检查 + 自动测试 + 自动打包"这套护栏。更妙的是：**配置页改成由 DSH 宿主自动生成表单**，连手写网页都省了。关键是——已经验证好的那十几条"插件↔主服务"通话约定一行不动。

**③ 为什么每个单元要独立钥匙、钉死单个账号？**
"单元"= 一个（渠道 × 账号 × 模型）的组合，是最小的可独立调用单位。我们要求：你点哪个单元，就一定走哪个账号，**绝不张冠李戴、绝不自动轮到别的账号**。原因很实在——养号场景下每个账号的额度、签到、任务是独立资产，一旦系统偷偷换号，会污染账号使用记录、还可能触发渠道风控。做法是**每个单元发一把独立访问钥匙，钥匙和单元绑死**；该账号不可用就直接报错，绝不偷偷顶替。（实现有甲/乙两案，见第 6 节拍板项②，已推荐甲。）

**④ 为什么把"养号"定为主线，而不是只做个转发？**
这套系统真正的价值不是"把请求转出去"，而是"**自动把账号养起来**"——每天签到、做任务、领 Pro/额度、保持在线，账号才续得上额度、才不会被上游注销。尤其 WorkBuddy 的"保活"是刚需：上游会定期掐断登录会话，不主动刷 token 就会一批账号全部登录失效。所以主线从"纯转发"升级成"**转发 + 养号一体化**"。

> 顺带说一个"思考强度"的小规矩：调用时如果带了"思考强度"参数（让模型多想还是少想），渠道支持就按它的规则传过去，不支持就用默认值，**一律不报错、不中断你的对话**。

## 5. 改造阶段（5 步，每步做什么、出什么、谁验收、风险）

| 阶段 | 做什么 | 产出什么 | 谁能验收 | 大概风险 |
|---|---|---|---|---|
| **阶段一：后端瘦身 + 小补丁** | 删掉第 3 节里列的赘肉；补三个小补丁：就绪探针 `/readyz`、优雅停接口 `/shutdown`、两处配置"防写半截"；收掉旧冗余接口 | 一个能跑的**瘦身版主服务 exe** | 开发自测：跑通一条转发请求、签到接口能调、自动测试全绿 | 删模块时可能牵连一处编译引用，逐个解即可，可控 |
| **阶段二：渠道插件定稿** | 按养号能力保留 workbuddy/qoder/trae，zcode 待定；那个干净版 workbuddy 插件要自己编译成 dll | `plugins/` 下几个渠道 dll | 开发：每个 dll 能被 exe 加载，签到/领奖/余额接口都通 | 干净版插件是按旧版 SDK 编的，要实测一次"能不能被新主服务加载" |
| **阶段三：DSH 插件 TS 化 + 单元机制** | 照规范范本把插件改成 TS；做首启自动下载/配置/拉起、单元列表、养号开关、状态页；落地"每单元独立钥匙钉死账号"（方案甲） | 一个能装进 DSH 的**插件包** | 你（决策者）：在 DSH 里启用后能看到页面、单元按账号锁死、带思考强度也不报错 | 钉账号那约 10 行后端改动要和阶段一对齐，别两边打架 |
| **阶段四：开箱即用串联 + 加固** | 打通首启全流程（下载→校验→写配置→拉起→探活→页面回显）；加崩溃自动重启（带退避，防崩了狂重启）；加"插件关了就顺手带走主服务"（不留孤儿进程） | 你**零配置**启用即用 | 你：在一台干净电脑上装插件，从头到尾不用手填任何东西 | 下载/校验链路、Windows 进程托管细节是主要坑点 |
| **阶段五：发布与分发（收尾）** | 定好"主服务 exe + 各 dll 必须成对升级"的规矩，出校验清单（SHA-256） | 可分发的产物包 + 校验清单 | 按清单完整装一遍无误 | 谁来编译发布（见拍板项⑥）——不定下来首启自动下载就没来源 |

## 6. 需要你拍板的事（6 件）

**① ZCode 这个渠道，留还是砍？**
它没有每日签到、没有任务，只有"领试用包/错峰优惠"，而且领试用包要你本人在浏览器过一道验证码，自动化程度低。
→ **建议**：如果这批号是新号、想薅试用包就**留**（但验证码做成手动按钮，别全自动）；如果已经是付费老号就**砍**。

**② "钉死单账号"用哪个方案？（已推荐甲）**
- **甲（推荐）**：后端加约 10 行，把"钥匙↔单元"映射喂给系统里现成的"指定账号"机制。最稳、最直接、行为最符合"绝不混用"。
- **乙**：后端一行不改，把账号编码进模型名里（比如 `某模型@账号1`），靠渠道插件去解析。省后端改动，但耦合到插件、不够干净。
→ **建议选甲**，代价是要在后端 fork 上动约 10 行（见⑤）。

**③ 养号默认值怎么设？（建议：自动签到开 / 自动任务关）**
- 自动每日签到：**默认开**（签到是日常收益，没风险）。
- 自动做任务：**默认关**（任务动作重、误触或触发风控的风险高，你明确开才跑）。
→ 确认这个默认，还是要改成别的。

**④ 账号怎么进系统？**（原计划"跳到旧网页导入"已随内置网页删除作废，得重选一条路）
- (a) **最省事**：你把账号登录文件（一个 json）放进指定文件夹，系统自动识别加载——零界面、零后端改动。
- (b) 插件页加个"导入账号"按钮，选文件上传——体验好一点，但后端要多开两条接口。
- (c) 在插件里走完整网页登录流程——最顺手但工作量最大。
→ 选哪条。

**⑤ 是否授权改动后端（CLIProxyAPI）这个 fork？**
方案甲、就绪探针、优雅停接口、防写半截、收旧接口，都要在这个开源项目的复刻版上动一点小手术（不是重写）。
→ 是授权"在 fork 上小改"，还是要求"尽量纯配置、不动后端"？（注意：选纯配置就只能退回拍板项②的方案乙，钉账号会没那么硬。）

**⑥ 谁负责编译并发布产物？**
主服务 exe 要在 Windows + 编译工具下生成；那个干净版 workbuddy 插件官方没有现成产物、得自己编。首启自动下载得有个固定的发布来源。
→ 定好谁来出这个发布包、谁维护校验清单，否则阶段四的"开箱即用"落不了地。

### 一句话收尾
> 一台 Windows、一个 DSH 插件、一把随机管理密码；主服务只裁不重写，渠道按养号能力取舍，界面全归插件；每个调用单元钉死一个账号，养号（自动签到/做任务/领奖/保活）是主线。剩下的，就是上面 6 件事等你拍板。
