## 二、新发现（4 项，影响方案精度 → 已同步决策记录/待实施验证）

### 发现 1（利好）：宿主原生已具备"按请求钉号"的完整入口
`sdk/api/handlers/model_execution.go:115/151`：
```go
if req.AuthID != "" {
    ctx = WithPinnedAuthID(ctx, req.AuthID)
}
```
即 `ExecuteModel` / `ExecuteModelStream` 两个内部模型执行入口**已经支持 req.AuthID → 钉号**。
→ **对方案甲的影响**：key→unit 映射的实现路径比详案（access 中间件 + WithPinnedAuthID 注入）更顺——只需把"单元 key 解析出的 authID"作为请求 AuthID 传入，宿主新增代码可进一步收敛（约 5-10 行），甚至可能不碰 access 中间件、只在进入 ExecuteModel 前注入 req.AuthID。实施时优先评估此捷径。

### 发现 2（删除面遗漏）：`internal/browser` + `sdk/auth/{claude,codex,...}` 内置 OAuth 族
- `internal/browser/browser.go` 存在，被 `sdk/auth/{antigravity,claude,codex,codex_device,devin,kimi,meta,xai}.go` 引用（内置 provider 的浏览器 OAuth 登录辅助）。
- 这些**不属于插件渠道**（插件渠道用自己的登录协议），与详案"删内置 executor"同族，但详案删除清单未列入 `internal/browser` 与 `sdk/auth` 的内置 OAuth 族。
- 组织者 CLIProxyAPI 探查员（s_000cHCK2uS2）也独立发现 `internal/browser 未列入删除清单`——两条线互相印证。
- **处理**：列入待实施删除项；删前必须 grep 确认 `sdk/api/handlers` 的 /v1 OAuth callback 路由（详案 §5 已列 5 条待删）删除后无残留引用；`sdk/auth` 需确认是否有插件渠道共用（workbuddy 插件有自己的 authfile.go，不依赖宿主 sdk/auth → 大概率可整族删，实施时验证）。

### 发现 3（生命周期注意点）：插件 shutdown 是 no-op，宿主重启碰 Go sync 原语会 SIGSEGV
`plugins/workbuddy/checkin.go` 顶部注释原文：
> "there is deliberately no stopCheckinScheduler. The plugin shutdown export is a no-op ... because the host invokes it during its own runtime teardown, where touching Go sync primitives from the plugin's c-shared runtime caused SIGSEGV on every restart."
→ **对进程托管设计的影响**：DSH 插件停 CPA 时，**不要依赖插件 shutdown 清理调度器**；进程终止应走"shutdown 端点 → Ctrl-C → taskkill /F 兜底"，与产物 2-A/2-C 现有设计一致（此发现是佐证而非修改）。

### 发现 4（原子写第 3 处）：`internal/config/config_load.go:223`
`os.WriteFile(configFile, cleaned, 0600)`（配置加载清洗后回写）——与 config_yaml.go:102 同属 config 写路径，若 watcher 监听同一文件，此点也建议并入原子写补丁范围（补丁从 ×2 扩为 ×3，工作量仍 <30 行）。
