## 0. 三版共同基线（差异只在模块怎么排）

以下在三版中**完全一致**，不再每版重复：

1. **M4 设置永远由宿主 schemastery 自动渲染**（连接/生命周期/units[] 声明/全局思考强度），client.js 不写配置 JSX。三版都只是"在它下方追加一个自定义运行态区块"（`plugins.detail.section`），不把设置搬进自定义 React。
2. **M1 状态条常驻**（StateDot done/ongoing/error + `127.0.0.1:<port>` + 条件渲染[启动]按钮 + {⚠无管理密钥} Tag），在自定义区块顶部，跨模块常驻。
3. **单元行三段式标识**（照专项 §2，不重画）：`{渠道Tag 固定tone}` `账号昵称 label-primary` `模型短名 label-secondary`，尾部状态徽标组（启用 solid / 禁用 danger / 签到 success / 余额低 warning）+ 启用 Switch + 行级[签到]按钮。行上永远带一个"对话可选"事实：enabled 且 live = picker 里可见；禁用 = 灰显且 picker 不可选。
4. **交互铁律**：行级 busy 锁（`ReadonlySet<authIndex+kind>`）；批量签到/任务必走 primitives `Modal`（"将对 N 个账号执行"）；20s 轮询 + visibilitychange 暂停 + 读编号最新赢；失败不擦屏、行内错误条（12px tertiary 几何、只换 `--dsw-alias-state-error-primary`）；空/未知渲染 null 不摆假 0；删拖拽/汇总条/进度条/management.html 外链引导。
5. **组件/皮肤**：卡壳用 `DisclosureRow expandOnRowClick`（icon=StateDot）；弹层 portal→body + `--dsw-specific-menu`+`--dsw-menu-backdrop-filter` 成对写 `::before` + `isolation:isolate` + `--dsw-elevation-prominent`；focus ring 一行式；中性边框 0.5px；数字 `tabular-nums`；禁用用 `--dsw-alias-label-dimmed` 不用 opacity。

> 三版的唯一差异 = **M1/M2/M3 三个运行态模块在自定义区块内怎么排**：竖排单流 / SegmentedTabs 分页 / 渠道分组卡片。

## 方案一　极简单页流

**一句话**：一个页面从上到下 M1 状态条 → M2 单元区 → M3 养号操作条，零模块级导航，滚到底就是全部。

### 信息架构

```
层级：0 级（无模块级导航）
M1 状态条（常驻顶）
M2 单元区：渠道过滤 Pill（全部/WB/Tr/Qo/Zc）+ [+新建单元] + 单元表（渠道分组小标题）
M3 养号条：全局自动签到/自动任务 Switch + [全部签到][全部任务][刷新]
（M4 设置 = 宿主表单，在本区块上方由宿主渲染，页面底部一行指引）
```

- 渠道维度 = Pill 过滤 + 行内 {渠道Tag}（过滤是临时切片，不改页面）。
- 养号操作 = 一条全局操作条，对"当前过滤出的单元"生效。
- 主任务路径：打开插件页 → 直接看到单元表 → 点行内[签到]，两步以内。

### 界面布局示意（ASCII 线框）

```
┌─ dsh-cpa-panel ─────────────────────────────────────────────┐
│ ● 运行中 · 127.0.0.1:8317   [启动]   {⚠无管理密钥}          │ M1 状态条
├─ 单元管理 ──────────────────────────────────────────────────┤
│ 渠道: [(全部)] [WB] [Tr] [Qo] [Zc]            [+ 新建单元]  │ M2 过滤+新建
│ ┌ WorkBuddy ──────────────────────────────────────────────┐ │
│ │ {WB} 陈盛泷 · claude-sonnet-4   ●启用 余12.4k ✓已签 [✓][签]│ │
│ │ {WB} cherry · claude-sonnet-4    ○禁用 余800   未签   [ ][签]│ │
│ ├ Trae ────────────────────────────────────────────────────┤ │
│ │ {Tr} 阿泉 · glm-4.6             ●启用 余5.0k  连签12 [✓][签]│ │
│ └──────────────────────────────────────────────────────────┘ │
├─ 养号 ───────────────────────────────────────────────────────┤
│ [✓]自动签到  [ ]自动任务  [归一调度]   [全部签到] [全部任务]  │ M3 操作条
├─ 设置 ───────────────────────────────────────────────────────┤
│ 连接/生命周期/单元声明/思考强度默认 → 见上方宿主自动表单      │ 指引（M4）

```

### 适用场景与优劣

| 优 | 劣 |
|---|---|
| 层级最少，开箱即懂，新用户 30 秒找到签到按钮 | 单元上到 ~25+ 行时单页偏长，M3 被推到折叠线外 |
| 与《UI-UX 专项》§1 已定稿的 M1→M2→M3 竖排**完全一致，零分叉** | 没有独立"总览"视图：跨渠道健康要靠肉眼扫行 |
| 工程量最小（就是专项线框，client.js 增量改即可） | 养号条是全局的，无法表达"某渠道单独自动签到"的分化 |
| 主任务（看单元/签到）无任何额外点击 | — |

**适用**：个人用、单元 ≤15、四渠道节奏一致。**这是默认基线版**。

## 方案二　分 Tab 模块化

**一句话**：M1 状态条常驻顶部，M2/M3 装进 SegmentedTabs 三个页签（总览 / 单元 / 养号），职责切得最干净。

### 信息架构

```
层级：1 级（模块级 SegmentedTabs；M1 不进 Tab）
M1 状态条（常驻顶）
Tab[总览]：四渠道各一张迷你健康行（账号数/今日已签/余额概览/签到支持与否）
Tab[单元]：渠道过滤 Pill + [+新建单元] + 单元表（方案一 M2 的全部）
Tab[养号]：全局开关 + 批量按钮 + 最近签到结果列表
（M4 设置 = 宿主表单；本 Tab 区不放"设置"页签——它由宿主渲染，插一句指引即可）
```

- 渠道维度 = 总览页一行渠道摘要 + 单元页的 Pill 过滤，双重视角。
- 养号操作 = 独立 Tab，与单元表物理分开，批量/记录有地方放。
- 主任务路径：打开插件页 → 默认落[总览] → 切[单元] → 操作。比方案一多一次 Tab 切换。

### 界面布局示意（ASCII 线框）

```
┌─ dsh-cpa-panel ─────────────────────────────────────────────┐
│ ● 运行中 · 127.0.0.1:8317   [启动]                          │ M1
│ ┌─────────┬─────────┬─────────┐                             │
│ │ (总览)  │  单元   │  养号   │   ← SegmentedTabs          │
│ └─────────┴─────────┴─────────┘                             │
│ ┌─ 总览 ────────────────────────────────────────────────┐  │
│ │ {WB} WorkBuddy   3 账号 · 今日 2/3 已签 · 余 13.2k     │  │
│ │ {Tr} Trae        2 账号 · 今日 1/2 已签 · 余 5.0k      │  │
│ │ {Qo} Qoder       1 账号 · 签到不支持                  │  │
│ │ {Zc} Zcode       1 账号 · token 单位                  │  │
│ └────────────────────────────────────────────────────────┘  │
│ （[单元]页 = 方案一 M2 整段；[养号]页 = 全局开关+批量+记录） │
└──────────────────────────────────────────────────────────────┘
```

### 适用场景与优劣

| 优 | 劣 |
|---|---|
| 职责最分明：每个 Tab 回答一个问题；未来加"签到记录/用量统计"直接加 Tab 不挤单页 | 主任务（看单元/签到）多一次 Tab 切换——养号是高频主线，多一跳 |
| 总览 Tab 给跨渠道健康一个正式落点 | SegmentedTabs 有键盘/aria 成本（专项 §5 明确"渠道分组用 Pill 不做 SegmentedTabs"——本版把 SegmentedTabs 用在**模块级**而非渠道级，方向不冲突，但仍是官方更重的控件） |
| 养号记录/批量操作有专属地盘，不跟单元表抢视觉 | Tab 激活态要自己持久化（或落 URL hash），刷新后回到哪页要定义 |
| 功能膨胀时扩展性最好 | "设置"不能真放进自定义 Tab（M4 归宿主），Tab 数天然只有 3，第四个只能是指引卡 |

**适用**：单元 25+、养号记录/统计需求会膨胀、团队多人使用。**是"规模大了以后"的演进形态，不是第一版默认**。

## 方案三　分组卡片式

**一句话**：渠道升为一级对象——每渠道一张 `DisclosureRow` 折叠卡，卡内放该渠道的养号操作与单元行；渠道与账号成为两个独立层级。

### 信息架构

```
层级：1 级（渠道为一级卡；卡内单元行为二级）
M1 状态条（常驻顶）
每渠道一张 DisclosureRow 卡（icon=StateDot 渠道健康；collapsedContent="3 账号 · 今日 2/3 已签"）
  卡内：渠道级操作条（本渠道 autoCheckin Switch + [全部签到][全部任务]）+ 本渠道单元行列表
（M4 设置 = 宿主表单，不变）
```

- 渠道维度 = 一级卡（独立、可折叠、有自己的状态行）；账号维度 = 卡内行。**"渠道账号独立呈现"在三版中最彻底**。
- 养号操作粒度落到渠道级（上游 auto-checkin/批量 action 本来就是 `?plugin=<channel>` 粒度，UI 与 API 粒度天然对齐）。
- 主任务路径：打开插件页 → 展开目标渠道卡 → 点行内[签到]。默认全部折叠时是"渠道总览"，展开一个渠道才看到单元。

### 界面布局示意（ASCII 线框）

```
┌─ dsh-cpa-panel ─────────────────────────────────────────────┐
│ ● 运行中 · 127.0.0.1:8317   [启动]                          │ M1
├──────────────────────────────────────────────────────────────┤
│ ▸ {WB●} WorkBuddy        3 账号 · 今日 2/3 已签              │ 折叠卡
│ ▾ {Tr●} Trae             2 账号 · 今日 1/2 已签              │ 展开卡
│   ┌──────────────────────────────────────────────────────┐   │
│   │ [✓]自动签到(本渠道)        [全部签到] [全部任务]      │   │ 渠道级操作
│   │ ────────────────────────────────────────────────    │   │
│   │ {Tr} 阿泉 · glm-4.6     ●启用 余5.0k 连签12 [✓][签]  │   │ 单元行
│   │ {Tr} 小七 · glm-4.6     ○禁用 余200   未签   [ ][签]  │   │
│   └──────────────────────────────────────────────────────┘   │
│ ▸ {Qo○} Qoder            1 账号 · 签到不支持                 │
│ ▸ {Zc-} Zcode            1 账号 · token 单位                 │
└──────────────────────────────────────────────────────────────┘
```

### 适用场景与优劣

| 优 | 劣 |
|---|---|
| "渠道×账号"两级最直观，渠道是一等公民（独立卡、独立状态、独立操作） | 四渠道全展开时页面最长；默认折叠则单元详情多一次展开 |
| 渠道级开关/批量天然落位（与上游 `?plugin=` 粒度对齐） | 跨渠道扫"对话里能选哪些模型"要逐卡展开，不如单表直接 |
| 与 bridge 已验证的"每变体一张 DisclosureRow 卡"（WorkBuddyCard，B1 §2.5）同构，壳照抄零发明 | 渠道固定 4 个，卡片数不会增长；若未来渠道增减，卡数跟着走（可接受） |
| 折叠头 `StateDot + collapsedContent` 本身就是渠道健康总览，不需要方案二那个独立总览 Tab | "全部签到"全局动作被拆到各卡，跨渠道批量要逐个点（或顶部补一条全局条） |

**适用**：用户心智按渠道组织、各渠道养号节奏需要分化（如 WB 开自动签到、Tr 不开）。

## 4. 三版横向对比

| 维度 | 一·极简单页流 | 二·分 Tab 模块化 | 三·分组卡片式 |
|---|---|---|---|
| 模块级导航 | 无（竖排滚动） | SegmentedTabs（总览/单元/养号） | 无模块导航；渠道卡即导航 |
| 渠道维度呈现 | Pill 过滤 + 行内 Tag（切片，不独立） | 总览 Tab 摘要 + 单元页过滤 | **一级 DisclosureRow 卡（最独立）** |
| 账号维度呈现 | 单元表行 | 单元表行 | 渠道卡内行 |
| 养号操作粒度 | 全局一条 | 独立 Tab 全局 | 每渠道一条（+ 可选全局条） |
| 总览视图 | 无（肉眼扫行） | 有（总览 Tab） | 折叠头即总览 |
| 主任务点击深度 | 2 步（开页即单元表） | 3 步（开页→切 Tab→行） | 3 步（开页→展开卡→行） |
| 单屏信息密度 | 高（全在一页） | 低（每 Tab 一块） | 中（折叠态很疏，展开后高） |
| 可扩展性（加功能） | 差（长页） | **最好（加 Tab）** | 中（加卡内分区） |
| 工程量 | **最小**（≈专项已定稿线框） | 中（Tab 容器 + 三屏 + 状态持久化） | 中（渠道卡容器 + 卡内行复用单元行） |
| 与《UI-UX 专项》的关系 | **完全一致**（专项 §1 线框即此版） | 演进方向（专项把 M2/M3 竖排，本版改 Tab） | 渠道分组的强化版（专项 M2 的渠道 Pill 升级为卡） |
| 风险 | 单元多了页长 | 主任务多一跳；设置 Tab 是指引空槽 | 折叠态隐藏单元，发现性弱 |

三版共同满足验收底线：DSH 原生 ModelSelect 直接选单元（链路在宿主侧 registerAdapter，三版都不破坏）；单元行三段式标识齐全；渠道与账号两个维度都可见；不碰 CPA 内置 UI；全部 primitives + `--dsw-*` token。

## 5. 推荐结论

**默认选方案一（极简单页流）作为第一版落地形态**，理由：

1. 它就是《UI-UX 专项设计》§1 已经定稿的 M1→M2→M3 竖排线框——组织总装时**零分叉**，不会与专项冲突。
2. 养号是高频主线，主任务 2 步可达；工程量最小，正好落在"client.js 保留 JS 增量改"的路径 B 上。
3. "渠道账号独立呈现"靠 M2 内的渠道分组小标题 + Pill 过滤 + 行内 {渠道Tag} 已经成立，不需要为"渠道独立"额外上卡片。

**什么时候切走**（预留演进路径，不在第一版做）：

- 若各渠道养号节奏开始分化（WB 自动签到、Tr 手动）、或每渠道需要独立的自动任务开关 → **升级到方案三**（渠道 Pill 过滤替换为渠道 DisclosureRow 卡，单元行组件原样搬进卡内）。
- 若单元规模膨胀到 ~30+、或要加"签到记录/用量统计"独立视图 → **升级到方案二**（把 M2/M3 拆 Tab，M1 状态条保留常驻）。

**切换成本刻意压低**：三版共用同一个单元行组件（三段式徽标 + 状态徽标 + Switch + 行级按钮）与同一套轮询/错误/空态 hook；变的只是容器（竖排 / Tab / 渠道卡），行内逻辑与端点映射一行不改。第一版按方案一写，容器抽象好，后两版是换壳不是重写。
