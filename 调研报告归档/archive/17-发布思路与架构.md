# 发布思路与架构（供用户自行发布，我方不执行）

> 用途：给"我自己开发插件并发布"的完整路线图——产物清单、构建链、Release 流程、SHA-256 校验、版本成对升级、插件商店分发路径、CI 建议、发布检查清单。
> 依据：产物2-A/B/C + 融合总纲 §8 V1-V31 + 轮子地图 + ABI 兼容核验 + 蓝图复查（M1-M5、L4）。
> 状态：只读设计；用户自行执行发布。

## 0. 一句话

**发布物 = 4 件套（瘦身 exe + 4 个渠道 dll zip + SHA-256 清单 + DSH 插件包），全部挂 GitHub Release，DSH 插件首启按 SHA-256 校验后拉取落地；渠道 dll 与宿主 exe 按 SDK 钉版成对升级。**

## 1. 产物清单（四件套）

| # | 产物 | 内容 | 来源 | 形态 |
|---|---|---|---|---|
| 1 | `cli-proxy-api.exe` | 瘦身宿主（A 裁剪 + 补丁） | CLIProxyAPI fork，`build-local.ps1` 构建 | 单文件 ~15-25MB（cgo），Windows amd64 |
| 2 | `cpa-multi-plugins-windows-amd64.zip` | workbuddy/qoder/trae/zcode 四个 .dll | cpa-multi-plugins fork，CI（MSYS2 MINGW64）构建 | 扁平 4 个 .dll |
| 3 | `SHA256SUMS.txt` | 上述所有产物 + 插件包的 SHA-256 摘要 | 发布时生成（`sha256sum` / `Get-FileHash`） | 文本清单 |
| 4 | `dsh-cpa-panel-<ver>.tgz` 或 npm 包 | TS 化后的 DSH 插件（lib/index.js + index.d.ts + client.js + locale） | dsh-cpa-panel fork，tsdown 构建 | 插件包 |

**注意（蓝图复查 M1）**：`workbuddy-bridge-0.1.2-source` 是**未发布的工程范本仓库**，不产出 dll；实际投放渠道 = cpa-multi-plugins 的 `workbuddy.dll`。若需要 bridge 式纯转发对照，需另行用 `-buildmode=c-shared` 自编 `workbuddy-bridge.dll`（命令与 cpa-multi-plugins scripts/build.sh 逐字同款），并在 SHA256SUMS 里单独列。

## 2. 构建链（Windows 产物从哪来）

### 2.1 宿主 exe
- **主路径（已验证）**：`build-local.ps1`——`CGO_ENABLED=1` + 仓库自带 `.toolchain/mingw64/gcc.exe` + `go build -ldflags="-s -w" -o cli-proxy-api.exe ./cmd/server`（Go 1.26）。
- **可选路径**：`CGO_ENABLED=0 go build`（loader_windows.go 纯 syscall，理论可行；需冒烟确认 dll 加载，对应验证点 V5）。建议先 CGO=1 出可用包，CGO=0 作为后续优化。

### 2.2 渠道 dll（c-shared）
- 必须 `CGO_ENABLED=1` + Windows C 编译器（MSYS2 MINGW64 `mingw-w64-x86_64-gcc`）。
- 构建命令（cpa-multi-plugins release.yml:71-118 现成）：`CGO_ENABLED=1 CC=gcc go build -buildmode=c-shared -trimpath -ldflags="-s -w" -o <id>.dll .`
- 每个插件独立 go.mod，**钉 SDK `github.com/router-for-me/CLIProxyAPI/v7 v7.2.30`**（ABI 兼容已核验：v7 编译 dll 可加载 v8 宿主，ABIVersion=1 一致、SchemaVersion 1vs6 协商向后兼容）。
- 发布前必须改：`release.yml` PLUGINS 去掉 `mimo`（改 4 个）、冒烟配置块（241-248 行）同步去 mimo（蓝图复查 L4）；`scripts/build.sh` 插件清单补 `zcode`（当前只有 3 个）。

### 2.3 DSH 插件包
- `tsdown` 产出 `lib/index.js`（宿主 ESM）+ `lib/index.d.ts` + `lib/client.js`（浏览器半端原样）+ `locale/`。
- 发布前 `pnpm check`（typecheck → build → test）零错为硬门禁。

## 3. Release 发布流程（GitHub）

### 3.1 版本语义
- 宿主 exe：`v1.0.0` 起，语义化（breaking 变更升 minor；补丁升 patch）。
- 插件 zip：独立 tag 或随宿主 tag 带后缀（如 `v1.0.0-plugins`）。
- DSH 插件：npm/package.json version，tag `vX.Y.Z`。
- **成对升级规则（关键）**：宿主升 `ABIVersion` 大版本时，所有渠道 dll 必须用新 SDK 重编并同发；正常升级（SchemaVersion 协商兼容）时 dll 可滞后。发布页放一张兼容表（见 §5）。

### 3.2 Release 内容模板
```
Release v1.0.0
├─ cli-proxy-api.exe                (Windows amd64)
├─ cpa-multi-plugins-windows-amd64.zip  (4 dll)
├─ dsh-cpa-panel-v1.0.0.tgz
└─ SHA256SUMS.txt
附：CHANGELOG.md（本轮改了什么）+ 兼容表（宿主 SDK ↔ 插件 SDK）
```

### 3.3 SHA-256 清单格式
```
<64位hex>  cli-proxy-api.exe
<64位hex>  cpa-multi-plugins-windows-amd64.zip
<64位hex>  dsh-cpa-panel-v1.0.0.tgz
```
- 生成：Linux `sha256sum * > SHA256SUMS.txt`；Windows `Get-FileHash -Algorithm SHA256`。
- **DSH 插件首启按此清单校验**（bootstrap.ts verifyDll）：文件平台校验 → SHA-256 比对 → 通过才解压落地；失败不拉起、不静默用旧文件（验证点 V16）。

## 4. DSH 插件分发路径（两条）

| 路径 | 做法 | 适用 |
|---|---|---|
| **A. 本地投放（推荐首版）** | 用户把插件包放进 DSH profile `node_modules/`（cordis.patch.yml insert 已声明），exe/dll 由插件首启从 Release URL 拉取 + SHA-256 校验 | 私有/个人使用、不依赖商店审核 |
| **B. 插件商店（registry.json）** | cpa-multi-plugins 的 `registry.json` 目前**无 `install.artifacts`**（蓝图复查已确认），需补 artifacts 字段（URL+SHA256+platform）才能在 `plugins.store-sources` 在线安装 | 想公开分发时 |

- 商店路径建议：DSH 插件本体走 DSH 插件市场（cordis.patch.yml + package.json 元数据）；exe/dll 走 GitHub Release + SHA-256（首启拉取），不塞进 npm 包（体积与更新解耦）。

## 5. SDK 版本兼容表（发布页必附）

| 宿主 exe SDK | 插件 dll SDK | ABIVersion | SchemaVersion | 能否直接加载 |
|---|---|---|---|---|
| v8（本项目） | v7.2.30（现钉） | 1 = 1 | 6 vs 1（协商向后兼容） | ✅ 可直接加载（已核验） |
| v8 升级 minor | v7.2.30 | 1 = 1 | 6 vs 1 | ✅ |
| 宿主升 ABIVersion=2 | 必须重编 v2 | 1 ≠ 2 | — | ❌ 加载被拒（loader_windows.go:117 校验挡） |

**规则**：ABIVersion 是硬门禁（不等即拒载）；SchemaVersion 走协商向后兼容（宿主容忍旧值）。升级宿主 ABIVersion → 插件集必须同版重编同发。

## 6. CI 建议（用户可选用）

```yaml
# .github/workflows/release.yml（精简骨架）
jobs:
  build-host:      # ubuntu/windows: go build 瘦身宿主 → cli-proxy-api.exe
  build-plugins:   # windows: MSYS2 MINGW64 → 4 个 c-shared dll → zip
  build-plugin:    # node: pnpm typecheck && pnpm build → dsh-cpa-panel tgz
  checksums:       # sha256sum → SHA256SUMS.txt（依赖前三 job）
  release:         # softprops/action-gh-release 打 tag 发布（依赖 checksums）
```
- 关键点：插件必须 cgo 构建（MSYS2）；宿主可用纯 Go（CGO=0 冒烟后）；发布前跑 V31 投放冒烟（4 dll register 成功）。

## 7. 发布检查清单（发布前逐项）

- [ ] `go build ./...` + `go vet` 零错（宿主瘦身后硬门禁）
- [ ] 验证点 V1-V3 冒烟通过（ABI 账号面板/流式/auth 回调，用 workbuddy.dll 不是 bridge）
- [ ] V26 qoder cf5f6af 首登奖励实测通过（上游改版→回滚评估）
- [ ] V31 Windows 投放冒烟：4 dll 进 plugins/ 后 plugin.register 成功、auth 收养、/accounts 可访问
- [ ] SHA256SUMS.txt 与 Release 附件一一对应（文件名精确匹配，DSH 首启按此解析）
- [ ] 兼容表更新（若 SDK 钉版变更）
- [ ] CHANGELOG 写明：删了什么（R13 内置族）、加了什么（单元/养号/UI）、breaking 提示
- [ ] 插件包 `pnpm check` 通过；`dsh.client.inject` 补了 primitives（蓝图复查确认的既有 bug）
- [ ] 回滚预案写进 CHANGELOG：渠道出问题换旧 dll（按 .dll 粒度）、DSH 端可锁旧版本

## 8. 风险与回滚（发布视角）

| 风险 | 处置 |
|---|---|
| 上游渠道协议改版（签到/任务/首登奖励） | **按 .dll 文件粒度回退旧版**；DSH 侧可单独关 tasks_auto/checkin_auto，转发不受影响 |
| CI 产线故障发不出 zip | 用上一 Release zip；scripts/build.sh 本地应急（补 zcode 后） |
| 宿主 ABI 升级 | 兼容表先行，插件集同版重编同发；旧 dll 保留可回退 |
| SHA-256 源不可达 | 插件首启报"下载失败"+重试；发布页与 README 放备用镜像 URL |
| 用户机器杀软误报 cgo exe | README 注明来源 + SHA-256 供核验；建议签名（可选，后续） |

---

**一句话收尾**：发布 = 构建 4 件套 → 打 GitHub Release（tag 语义化）→ 附 SHA256SUMS + 兼容表 → DSH 插件首启按清单校验拉取落地；渠道 dll 与宿主 exe 按 ABI 成对升级，回滚永远按 .dll 文件粒度，用户机零工具链。
