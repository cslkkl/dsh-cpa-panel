## 1. 项目背景（一句话）

把三个开源仓库（CLIProxyAPI / cpa-multi-plugins / dsh-cpa-panel）改造为一个**Windows 上开箱即用的 DSH 插件**：DSH 插件作为唯一界面，托管一个瘦身后的 CPA 本地进程，多渠道（WorkBuddy/Qoder/Trae/ZCode）账号自动养号（签到/领取/做任务/保活），并提供"渠道×账号×模型"独立调用单元，绝对锁定单账号不混用。

## 4. 已锁定方向（不可推翻，除非用户明确改）

1. 主功能 = **养号自动化**（签到/领取/做任务/保活）。
2. 独立调用单元：渠道×账号×模型 = 1 单元；每单元独立 API key（`units[].apiKey`）；用宿主原生 `pinned_auth_id` 钉号，**绝对锁定单账号不混用**；账号不可用直接报错不顶替。
3. 单元配置在 DSH 配置文件（插件 `units[]` schema）声明。
4. 思考强度：请求带 reasoning_effort/thinking → 按渠道能力映射/透传；无 → 默认 medium（每单元可覆盖）；不报错。
5. CPA 无关功能全删；**CPA 内置 UI 全删**（management.html/panel.html/assets），唯一 UI = DSH 插件页。**登录/凭证验证保留面（R13 澄清）**：插件渠道（WorkBuddy/Qoder/Trae/ZCode）的登录协议、auth 文件、验证流程 = 养号前提，**全部保留**（在 cpa-multi-plugins 插件集内）；宿主内置 provider 族（`internal/runtime/executor/{claude,codex,gemini,kimi,xai,devin,meta,antigravity,vertex,aistudio}*`、`sdk/auth/{claude,codex,codex_device,devin,kimi,meta,xai,antigravity}.go`、`internal/browser`）**全部删除**——插件渠道用自己的登录协议，不依赖宿主内置 OAuth。
6. 平台 = **Windows**；无 Docker、纯启动服务（单 exe）；插件 dll 从 Release 预编译分发（SHA-256 校验），用户机零工具链。
7. DSH 宿主**零改动**，一切通过插件实现（cordis.patch.yml 机制照旧）。
8. 后端保 Go 只裁剪（A 方案，保留 906 个测试），补丁：原子写×2、/readyz、/shutdown 端点、key→unit 映射、v0 ~90 条端点收敛。
9. 插件：宿主半端照 dsh-workbuddy-bridge 模板 TS 化；client.js 保留 JS 改造；schemastery 自动表单；进程托管（Job Object 父退子亡 + 退避重启 + 非 shell spawn）。
10. 渠道：workbuddy（全保留）/ qoder（签到+claim-pro+保活）/ trae（CN 签到）/ zcode（可选，薅试用包）；mimo 删；workbuddy-bridge 作 A/B 对照（不合并）。
11. 三仓库独立、不合并；垃圾零容忍（废接口/废函数/改名），唯一例外=无源码的 .dll 等二进制。
12. 过程中要求：不断确认、逐步修改、不做合并操作。

## 10. UI/UX 推倒重设计定稿（2026-10-03）

- **IA 四模块**（覆盖 2-C §2.3 旧混排）：M1 总览/状态（只读状态条）｜ M2 单元管理（渠道·账号·模型，增删改/启用/思考强度）｜ M3 养号（签到/任务/自动开关/批量）｜ M4 设置（宿主 schemastery 自动表单，零 JSX）。

- **DSH 模型直选链路（bridge 实证，非臆测）**：宿主侧 `inject:['llm']` + `ctx.llm.registerAdapter()` → provider id=渠道、model id=`<模型>@<authRef>`、显示名=`<账号昵称> · <模型名>`、baseUrl=`http://127.0.0.1:8317/v1`、resolveApiKey=units[].apiKey → DSH 对话窗原生 ModelSelect 直接选单元。**唯一未决**：CPA 按 model id 精确钉 auth 是否成立 → 待验证条目 V3（与方案甲 key→unit 是同一问题的两面）。
- **UI 三方案**：方案一极简单页流（**默认第一版**：M1→M2→M3 竖排、主任务 2 步、与专项零分叉、工程量最小）；方案二分 Tab（规模 30+ 时演进）；方案三渠道分组卡片（渠道节奏分化时演进）。三版共用单元行组件与交互铁律，换壳不重写。
- **交互铁律**：行级 busy 锁、批量必走 Modal 确认、20s 轮询+visibilitychange 暂停、失败不擦屏行内错误条、空/未知渲染 null 不摆假 0、删拖拽/汇总条/进度条/management.html 外链。
