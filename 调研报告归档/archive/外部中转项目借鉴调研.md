# 外部中转项目借鉴调研

> 调研目标：为"多供应商 API 中转/代理服务（CPA 类 ProxyAPI）"收集同类项目与架构借鉴。
>
> **本场景硬约束（所有判断都落到这组约束上）：**
> - Windows 单机运行一个**瘦身 Go 服务**；
> - 职责：账号/鉴权、请求转发、渠道选择、模型映射；
> - 由一个 **DSH 插件同机托管进程**，并渲染**简单配置页**；
> - **开箱即用**，不引入 Postgres / Redis / 多机部署等重型依赖。
>
> 调研日期：2026-10-03。每条结论后附可溯源 URL。

---

## 1. LiteLLM（Proxy 模式）

### 架构要点
- 形态：Python 单进程 Proxy（FastAPI），对外暴露统一 OpenAI 兼容端点；控制面（config.yaml + Admin Dashboard + 管理 API）与数据面（转发请求）在同一进程内，生产级才外挂 Postgres（Prisma）与 Redis（多实例共享路由状态）。["https://docs.litellm.ai/docs/proxy/configs","https://dev.to/toffy/top-5-ai-gateways-for-enterprises-79c"]
- `config.yaml` 四段式结构，是它最值得抄的配置范式：["https://docs.litellm.ai/docs/proxy/configs"]
  - `model_list`：每条 = 对外别名 `model_name` + `litellm_params`（`model: provider/xxx`、`api_base`、`api_key: os.environ/XXX`、可选 `rpm`/`tpm`）；
  - `router_settings`：`routing_strategy`（`simple-shuffle` / `least-busy` / `usage-based-routing` / `latency-based-routing`）、`model_group_alias`；
  - `litellm_settings`：`num_retries`、`request_timeout`、`fallbacks`（声明式失败回退链）、`context_window_fallbacks`、`allowed_fails`（连续失败 N 次则冷却该 deployment）、`drop_params`（静默丢弃下游不支持的参数）；
  - `general_settings`：`master_key`（调用方鉴权）、`alerting`。
- **同名 model 多条 = 同模型多渠道负载均衡**：多个 `model_name` 相同的条目即一组 deployment，按 `rpm/tpm` 加权挑选。["https://docs.litellm.ai/docs/proxy/configs"]
- 密钥与配额：Virtual Keys 体系——给调用方发的 key 可带 `max_budget`、`tpm/rpm_limit`、允许的 model 列表；key 级、user 级、team 级预算独立计数、任一超限即拒。["https://docs.litellm.ai/docs/proxy/virtual_keys","https://docs.litellm.ai/docs/proxy/users","https://deepwiki.com/BerriAI/litellm/3.3-user-team-and-key-management"]
- 管理面：自带 Admin Dashboard（React），可视化管 key/user/team、看 spend 分析；路由策略也支持按请求 tag 过滤。["https://deepwiki.com/mikeplavsky/litellm/5-admin-dashboard","https://docs.litellm.ai/docs/proxy/tag_routing"]

### 值得借鉴的具体点
1. **`model_name`（对外别名）↔ `litellm_params.model`（上游真实模型名）的两层命名**——这正是我们"模型映射"要做的事：客户端只认一个名字，网关内部翻译成上游模型名。
2. **同别名多 deployment + 可选加权** = 多账号轮询的最小实现；单机版只保留 `simple-shuffle` 即可。
3. **声明式 `fallbacks` 链 + `allowed_fails` 自动冷却**：某渠道连续失败就临时摘掉，恢复后再上——这是"开箱即用"稳定性的关键，不需要外部健康检查服务。
4. **`drop_params: true`**：上游不支持的参数不要报错，静默丢弃，避免不同渠道之间互相打架。
5. **`api_key: os.environ/XXX` 从环境变量读密钥**的写法——配置页里密钥字段不落盘明文时可参考。

### 本场景不需要的复杂度
- Postgres + Prisma 连接池调优、Redis 共享路由状态、多 worker 多实例部署——单机单进程全内存即可。["https://docs.litellm.ai/docs/proxy/configs","https://dev.to/toffy/top-5-ai-gateways-for-enterprises-79c"]
- Team/End-User 多层预算、SSO、Tag 预算、Slack 告警、Langfuse/BigQuery 日志导出——单机一个用户，最多保留"本机调用 key + 一个总开关"。["https://docs.litellm.ai/docs/learn/enterprise_quickstart","https://dev.to/kaz123/building-an-llm-cost-governance-dashboard-with-litellm-bigquery-115f"]
- `least-busy`/`latency-based` 这种需要全局 TPM 计数的策略，单机用轮询/加权随机足够。

## 2. OpenRouter

### 架构要点
- 形态：**纯 SaaS、不可自托管**，400+ 模型 / 70+ provider 聚合在一个端点后；本质是一个"路由编排层 + 计费层"，自己不跑推理。["https://openrouter.ai/blog/insights/llm-gateway/"]
- **路由三步规则**（可靠性优先、成本其次）：["https://openrouter.ai/blog/insights/reliability-failover/"]
  1. 优先选"过去 30 秒内无重大故障"的 provider；
  2. 在稳定候选里按**价格的反比平方**加权随机；
  3. 其余全部留作 fallback。
- 路由偏好可由客户端一行声明：`model` slug 加后缀 `:floor`（最便宜）/ `:nitro`（最快吞吐），等价于请求体里 `provider.sort: "price" / "throughput"`；也可 `provider.allow` 白名单指定只用哪些 provider。["https://openrouter.ai/blog/insights/model-routing/","https://openrouter.ai/blog/tutorials/how-to-get-the-lowest-cost-llm-inference-on-openrouter/","https://openrouter.ai/docs/guides/routing/provider-selection"]
- 密钥模式：平台统一发 key 计费；也支持 BYOK（自带上游 key），收正常推理价 5% 的手续费。["https://openrouter.ai/docs/guides/overview/auth/byok"]

### 值得借鉴的具体点
1. **"故障窗口记忆"思想**：不用做精细的健康检查探针，只要记住"某渠道最近 N 秒内报过错"就把它排到队尾——实现极轻（内存里一个时间戳即可），容错收益很大。
2. **`model:floor` / `:nitro` 这种后缀路由偏好**是一个很轻量的 UX 设计：客户端不改代码，只改模型字符串就能在"省钱/要快"之间切换。单机版可在配置页给用户两个预设按钮。
3. **provider 白名单**（allow 某些渠道）作为路由可选约束，比条件路由引擎简单。

### 本场景不需要的复杂度
- 70+ provider 的实时可用性大盘、价格反比平方加权、Zero Completion 计费、EU 区域锁定、SOC2 合规——这些是 SaaS 运营级能力。["https://openrouter.ai/blog/insights/llm-gateway/"]
- 按请求实时算钱、信用充值、5.5% 手续费——单机不需要计费闭环。

### 来源
- Provider 路由文档：https://openrouter.ai/docs/guides/routing/provider-selection
- 路由原理博客：https://openrouter.ai/blog/insights/model-routing/
- 自动故障转移：https://openrouter.ai/blog/insights/reliability-failover/
- BYOK：https://openrouter.ai/docs/guides/overview/auth/byok
- LLM Gateway 对比：https://openrouter.ai/blog/insights/llm-gateway/

## 3. one-api（songquanpeng/one-api）

### 架构要点
- 形态：**Go 单二进制，SQLite 默认即开箱即用**——与本场景（Windows 单机、瘦身 Go 服务）形态最接近。Docker 镜像一键起，默认端口 3000，默认 root/123456 首登强制改密。["https://github.com/songquanpeng/one-api"]
- 领域模型极其清晰（直接可抄的数据表设计）：["https://github.com/songquanpeng/one-api"]
  - **Channel（渠道）**：一个上游供应商接入点 = 类型 + 上游 key + 可选 Base URL + 该渠道支持的模型列表 + 分组 + 权重；
  - **Token（令牌）**：对外分发的 key，可设过期时间、额度、IP 白名单、允许的模型；
  - **Ability 表**：渠道 × 模型 的支持矩阵（"哪个渠道能跑哪个模型"），请求进来先按"目标模型"查 ability 表圈出可用渠道集合；
  - **用户分组 / 渠道分组**：不同组走不同渠道，组有倍率。
- 路由：不加指定时按权重在可用渠道里负载均衡；管理员令牌可在 key 后加 `-渠道ID` 强制指定渠道（`Authorization: Bearer sk-xxx-12`）。["https://github.com/songquanpeng/one-api"]
- 计费公式：`额度 = 分组倍率 × 模型倍率 × (prompt_tokens + completion_tokens × 补全倍率)`，补全倍率与上游官方对齐（GPT-3.5=1.33、GPT-4=2）。["https://github.com/songquanpeng/one-api","https://cn.x-cmd.com/install/one-api/"]
- 模型映射：支持把用户请求的模型名重定向到真实模型名；**官方明确警告：一旦设置模型映射，请求体会被重构而非透传，未正式支持的字段会丢**。["https://github.com/songquanpeng/one-api","https://gitee.com/fork-others/one-api"]
- 多机扩展才需要 MySQL + Redis + 主从同步（`NODE_TYPE=slave`、`SYNC_FREQUENCY`）；单机默认 SQLite 零依赖。["https://github.com/songquanpeng/one-api","https://gitee.com/blackfox/one-api"]

### 值得借鉴的具体点
1. **Channel / Token / Ability 三张表的领域划分**是本场景的最小数据模型范本：渠道表存上游、令牌表存本机调用 key、ability 表存"渠道→模型"索引。
2. **SQLite 单文件 + 单 Go 二进制 = 开箱即用**，与我们"Windows 单机"目标完全同构；前端 admin UI 也是单进程内置，不需要单独起前端服务。
3. **渠道测试按钮**：后台"测试连通性"，失败提示"返回不是 JSON 而是 HTML（通常是 IP 被 CF 封）"这类排错信息——配置页里一个"测试渠道"按钮极有价值。["https://github.com/songquanpeng/one-api"]
4. **令牌后加 `-渠道ID` 强制路由**是一个零成本的调试手段，DSH 插件排查问题时很有用。
5. **失败自动重试**：渠道失败后自动切下一个。["https://github.com/songquanpeng/one-api"]

### 本场景不需要的复杂度
- 在线充值、支付回调、邀请奖励、美元/人民币额度展示、公告、充值链接——这是"二次分发/SaaS"才有的东西。["https://gitee.com/fork-others/one-api","https://cn.x-cmd.com/install/one-api/"]
- 用户系统、用户分组、多用户注册——本机就一个用户，鉴权可简化为"一个本机固定 key 或直接免鉴权"。
- MySQL/PostgreSQL、Redis 缓存层、主从同步、watchtower 自动更新——单机 SQLite 足够。
- 完整倍率计费体系——本机最多记一下每个渠道用了多少 token 做展示，不必算钱。

### 来源
- 官方仓库 README（架构/部署/环境变量/额度公式全在这）：https://github.com/songquanpeng/one-api
- 功能清单 fork 镜像：https://gitee.com/fork-others/one-api
- 中文功能介绍：https://cn.x-cmd.com/install/one-api/

## 4. new-api（Calcium-Ion/new-api，one-api 的增强 fork）

### 架构要点
- 在 one-api 基础上把**渠道抽象做得更细**，是我们设计渠道配置表时最该逐字段抄的一个。渠道字段：["https://docs.newapi.pro/en/docs/guide/feature-guide/admin/channel"]
  - 基础：provider 类型、名称、API key；
  - 模型：勾选该渠道支持的模型列表，或"一键填充默认模型"；
  - 高级：`Base URL`（自定义上游地址）、`Priority`（数值越大越优先，默认 0）、`Weight`（同优先级内加权随机）、`Model Mapping`（JSON，用户模型名 → 上游真实模型名）、`Parameter Override`（JSON，强制覆盖请求参数）、`Auto Disable`（连续失败自动停用）。
- **多 Key 模式**：一个渠道下可挂多个上游 key，轮询策略可选 Round Robin（顺序轮）或 Weighted Random（加权随机）；**失败的 key 自动跳过，恢复后自动重新启用**。["https://docs.newapi.pro/en/docs/guide/feature-guide/admin/channel"]
- 运维操作：渠道列表展示名称/状态（绿=启用/红=禁用）/响应时间/已用配额；单行"测试"按钮 + 顶部"测试全部渠道"一键批量测；批量启用/禁用/打标签。["https://docs.newapi.pro/en/docs/guide/feature-guide/admin/channel"]
- 路由语义（社区文档复述）：先按 Priority 梯队选（主力→备胎），同 Priority 内按 Weight 随机；失败自动切下一渠道，最多重试 3 次。["https://devpress.csdn.net/awstech/6a91d51a3bda720d4b3588d8.html","https://blog.csdn.net/m0_61531676/article/details/158183730"]
- 支持的渠道类型除 OpenAI 兼容外，还有 Claude Messages、Gemini、Rerank、Suno、Dify ChatFlow、自定义完整地址等。["https://gitee.com/nmkxlc/new-api","https://toolerific.ai/ai-tools/opensource/Calcium-Ion-new-api"]

### 值得借鉴的具体点
1. **渠道字段表几乎可以直接照搬**：`{ 类型, 名称, BaseURL, Keys[], Priority, Weight, Models[], ModelMapping{}, ParamOverride{}, AutoDisable }`——这是我们 DSH 插件配置页的表单骨架。
2. **Priority（梯队）+ Weight（同梯队加权）两级调度**比纯随机更符合直觉：用户有"主力渠道 + 备胎渠道"的心智，配置页上两个数字就能表达。
3. **多 Key 轮询 + 失败 key 自动摘除/恢复**：用户在一个供应商下买了多个号时直接受益，不需要建多条渠道。
4. **Model Mapping 用 JSON 字典**（`{"请求名":"上游名"}`）比 one-api 文本映射更结构化，配置页可渲染成两列表格。
5. **渠道列表显示"响应时间"**：每次测试/请求回写一个 latency 字段，配置页一眼看出哪个渠道慢。
6. **Auto Disable 连续失败自动停用**：与 OpenRouter 的"30 秒故障窗口"异曲同工，但做成持久化开关更直观。

### 本场景不需要的复杂度
- 在线充值、支付、计费倍率体系、令牌分组的复杂权限矩阵。["https://blog.csdn.net/m0_61531676/article/details/158183730"]
- Redis 集群负载均衡、主从多机部署、渠道亲和性（同用户粘同一渠道减少冷启动）——单机单用户无此需求。["https://blog.csdn.net/m0_61531676/article/details/158183730","http://www.blog.faramita.space/archives/llm-new-api"]
- Midjourney/Suno 绘图/音乐渠道——我们只做 chat/completions 中转。

- 官方渠道管理文档（字段表/多 Key/测试操作全在这）：https://docs.newapi.pro/en/docs/guide/feature-guide/admin/channel

## 5. Dify 模型供应商插件架构

### 架构要点
- Dify 把"接一个新供应商"做成**插件**，由两部分组成：["https://enterprise-docs.dify.ai/en/3.11.x/develop/plugins/dev-guides-and-walkthroughs/creating-new-model-provider"]
  1. **Provider 配置 YAML**：声明供应商基本信息、支持的模型类型、**凭据 schema（credential schema）**；
  2. **Provider 类实现**：继承 `ModelProvider` 基类，核心方法是 `validate_provider_credentials(credentials)`——**发一次测试调用来校验用户填的 key 是否可用**。["https://enterprise-docs.dify.ai/en/3.11.x/develop/plugins/features-and-specs/plugin-types/model-schema"]
- 两个核心实体：**Provider**（管认证、列支持的模型）和 **AIModelEntity**（每个模型一条，声明类型/特性/参数 schema），全部是 Pydantic BaseModel——即"用 schema 描述自己"，前端据此动态渲染表单。["https://enterprise-docs.dify.ai/en/3.11.x/develop/plugins/features-and-specs/plugin-types/model-designing-rules"]
- 自定义模型时可在 YAML 里不预设参数，运行时按模型名动态决定参数 schema。["https://enterprise-docs.dify.ai/en/3.11.x/develop/plugins/features-and-specs/advanced-development/customizable-model"]

### 值得借鉴的具体点
1. **凭据 schema 驱动配置页表单**：DSH 插件的配置页不要硬编码 HTML，而是由后端声明"这个渠道类型需要哪些字段（name/type/base_url/key）"，前端自动渲染——加一种渠道类型只改后端 schema。
2. **`validate_provider_credentials()` 测试调用**：配置页上"保存前先点测试"按钮，就是发一个最便宜的 min completion 看是否 200，比让用户保存完才发现 key 错体验好太多。new-api 的"测试渠道"按钮是同一个思想，Dify 把它做成了供应商插件的强制契约。
3. **Provider（认证级别）+ Model（单模型级别）两层凭据校验**：如果未来要支持"一个渠道下不同模型用不同 key"，这个分层可直接套用；当前单层即可。

### 本场景不需要的复杂度
- 整个插件市场/插件上传/沙箱运行时、Python 插件 SDK、多租户工作区隔离——我们是同机单进程，渠道类型硬编码成 Go 内建即可，不必做插件系统。
- AIModelEntity 的完整参数 schema（temperature/top_p/max_tokens 约束等）——透传模式下不用管上游参数约束，配合 LiteLLM 的 `drop_params` 思想即可。

- 创建新模型供应商：https://enterprise-docs.dify.ai/en/3.11.x/develop/plugins/dev-guides-and-walkthroughs/creating-new-model-provider
- 模型 API 接口/凭据校验：https://enterprise-docs.dify.ai/en/3.11.x/develop/plugins/features-and-specs/plugin-types/model-schema

## 6. Portkey

### 架构要点
- 形态：声明式 JSON 路由配置，一次调用把"用哪些上游、怎么选"全部编码进去：["https://portkey.ai/docs/product/ai-gateway/configs","https://portkey.ai/docs/welcome/integration-guides/llama-index-python"]
  ```json
  { "strategy": { "mode": "fallback" },
    "targets": [ { "provider": "@anthropic-prod" },
                 { "provider": "@bedrock-prod" } ] }
  ```
  `mode` 可取 `fallback`（按序回退）/ `loadbalance`（按 weight 分摊）/ `conditional`（按请求元数据条件路由）；`targets[]` 里每项是一个 Virtual Key 引用 + weight。
- **Virtual Key**：把上游 key 集中存为受控对象，给业务方发的是 virtual key 引用而非原始 key；virtual key 可带预算上限、限流、安全存储。["https://portkey.ai/docs/virtual_key_old/integrations/libraries/cline","https://portkey.ai/docs/virtual_key_old/integrations/libraries/openai-compatible"]
- 可靠性件：fallback、指数退避重试、统一错误码、条件路由可与 loadbalance 嵌套组合（一个 loadbalance 集群整体再挂一个 fallback）。["https://portkey.ai/docs/product/ai-gateway/fallbacks","https://portkey.ai/docs/product/ai-gateway/load-balancing","https://portkey.ai/docs/guides/use-cases/combining-routing-strategies"]

### 值得借鉴的具体点
1. **`strategy.mode` + `targets[]` 的声明式路由 JSON**是一个非常紧凑的数据结构：我们的渠道配置完全可以落成 `{ strategy: "priority" | "weighted", targets: [ {channelId, weight} ] }` 这种结构，配置页渲染成列表即可。
2. **Virtual Key 即"上游密钥与调用方隔离"**：本机场景下虽然不发 key 给别人，但"上游 key 集中存、业务请求只引用别名"这个思想值得沿用——配置页里渠道 key 字段与转发逻辑解耦。
3. **"把一个负载均衡集群整体包进 fallback"**的嵌套思想：单机版可以先做平的（渠道列表按优先级+权重选），不必上嵌套。

### 本场景不需要的复杂度
- 条件路由引擎（按 metadata/header 选上游）、数据驻留合规路由、forward_headers 白名单、passthrough target——单机用不上。["https://portkey.ai/docs/guides/use-cases/combining-routing-strategies","https://portkey.ai/docs/product/ai-gateway/configs"]
- 云托管控制台、SLA、企业支持——Portkey 本体是 SaaS/商业产品，自托管能力有限。

## 8. 借鉴 / 不借鉴 汇总表

> 判定口径：✅ = 直接抄进我们的瘦身 Go 中转 + DSH 插件配置页；△ = 抄思想但极简实现；❌ = 本单机场景是过度设计。

| 能力点 | 来自 | 判定 | 落到本场景的做法 |
|---|---|---|---|
| **渠道 = 类型 + BaseURL + Keys[] + 支持模型列表** | new-api / one-api | ✅ | 配置页核心表单字段，直接照搬 |
| **Priority（梯队）+ Weight（同梯队加权）两级调度** | new-api | ✅ | 渠道表两列数字；请求先选最高优先梯队，内部加权随机 |
| **单渠道多 Key 轮询（Round Robin / Weighted Random），失败 key 自动摘除恢复** | new-api | ✅ | 一个渠道内挂多 key，内存记录各 key 最近失败时间 |
| **对外模型别名 ↔ 上游真实模型名 两层映射（JSON 字典）** | LiteLLM / new-api | ✅ | 配置页两列表格：客户端请求名 → 上游模型名；默认透传不重构请求体 |
| **同别名多渠道 = 负载均衡** | LiteLLM | ✅ | 与上面合并：一个对外模型可挂多个渠道 |
| **声明式 fallback 链 + 连续失败自动冷却/禁用** | LiteLLM / new-api / OpenRouter | ✅ | `allowed_fails=N`：连续失败 N 次摘除该渠道 X 分钟；`Auto Disable` 开关持久化 |
| **"最近 N 秒故障窗口"轻量健康记忆** | OpenRouter | △ | 内存里每渠道一个 `lastErrorAt`，30~60 秒内出错排到队尾，不做独立健康探针 |
| **渠道"测试连通性"按钮（发一次 min completion）** | new-api / Dify | ✅ | 配置页每个渠道行一个"测试"按钮 + "测试全部"，显示响应时间/报错 |
| **凭据 schema 驱动动态配置表单** | Dify | ✅ | 后端声明每种渠道类型需要哪些字段，DSH 插件前端渲染，加渠道类型不改前端 |
| **SQLite 单文件 + 单 Go 二进制 = 开箱即用** | one-api | ✅ | 我们直接照此形态：一个 exe + 一个本地 db/json，双击即起，不要求用户装 PG/Redis |
| **本机调用鉴权（一个固定 master key 或免鉴权仅监听 localhost）** | LiteLLM `master_key` | △ | 默认监听 127.0.0.1，可在配置页开一个简单 token；不做用户系统 |
| **每次请求落日志（model/latency/tokens/错误）** | Helicone / LiteLLM callback | △ | 配置页"最近请求"表格 + 每渠道累计用量，不做导出/BigQuery/Langfuse |
| **`drop_params` 静默丢弃上游不支持参数** | LiteLLM | ✅ | 转发前只白名单透传 chat/completions 标准字段，多余字段不报错 |
| **`-渠道ID` 强制指定渠道的调试手段** | one-api | △ | 可选实现：客户端 key 后加 `-{channelId}` 用于排查，默认不暴露 |
| **`model:floor` / `:nitro` 路由偏好后缀** | OpenRouter | ❌（v2 再说） | 单机用户量小，配置页里手动调优先级即可，不必做客户端字符串协议 |
| **多租户 / Team / End-User / 在线充值 / 支付 / 邀请奖励** | LiteLLM / one-api / new-api | ❌ | 单用户本机，完全不需要 |
| **Postgres + Prisma + Redis + 多 worker + 主从多机** | LiteLLM / one-api | ❌ | 单进程 SQLite/JSON 足够，集群状态全在内存 |
| **复杂计费倍率（分组倍率×模型倍率×补全倍率）** | one-api | ❌ | 最多显示"各渠道已用 token 数"，不做钱 |
| **least-busy / latency-based / usage-based 路由（需全局 TPM 计数）** | LiteLLM | ❌ | 单机轮询/加权即可，不上滑动窗口计数 |
| **条件路由引擎（按 metadata/header 选上游）** | Portkey | ❌ | 单机无多租户合规需求 |
| **完整插件市场 / Python 插件沙箱 / 多租户工作区** | Dify | ❌ | 渠道类型硬编码进 Go 二进制，加类型=发新版 |
| **企业特性：SSO / SOC2 / 区域锁定 / 审计日志导出 / Slack 告警** | LiteLLM / Portkey / Cloudflare | ❌ | 本机无合规要求 |
| **绘图/音频/图像渠道（Midjourney/Suno/Rerank）** | new-api | ❌ | v1 只做 chat/completions 中转 |

## 9. 给本项目的一句话结论

**数据模型照抄 new-api 的渠道字段表（类型/BaseURL/Keys/Priority/Weight/Models/ModelMapping/AutoDisable），进程形态照抄 one-api 的"单 Go 二进制 + SQLite + 内置管理页"，容错机制抄 LiteLLM 的"fallback + allowed_fails 冷却"和 OpenRouter 的"短期故障窗口"，配置页交互抄 Dify 的"schema 驱动表单 + 保存前测试凭据"。** 除此之外，多租户、计费、Redis/PG、集群、条件路由、企业合规全部是单机场景的过度设计，一律不做。
