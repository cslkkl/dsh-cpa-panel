# 多视角审视报告：最小裁剪 vs 模块重组 vs clean 重写

> 范围：五个本地仓库只读审视，为最终路线（A 最小裁剪 / B 模块重组 / C clean 重写）提供文件级论据。
> 对象：
> - `CLIProxyAPI`（Go 中转服务，`local-autobrowser`，module `.../v8`，go 1.26.0）
> - `cpa-multi-plugins`（Go c-shared 插件集）
> - `dsh-cpa-panel`（Cordis 插件，TS 迁移对象）
> - `workbuddy-bridge-0.1.2-source`（clean 单插件范本，2331 行）
> - `dsh-workbuddy-bridge`（TS 工程化参考）
> 方法：以磁盘上 9 份子代理报告为证据底座，缺口处直接查代码（只读，未改任何文件）。
> 三个待选方案在下文统一简称：**A=最小裁剪**（保留 CPA 宿主+插件 .dll，删无关模块）、**B=模块重组**（在现有结构上重分层）、**C=clean 重写**。

---

## 0. 全局速览（先给结论）

| 仓库 | 体量事实（实测） | 一句话定性 |
|---|---|---|
| CLIProxyAPI | **非测试 .go 735 个 / 测试 .go 761 个** | 一个**被测充分的胖单体**；赘肉是"已被边界隔开的可删模块"，不是"核心耦合" |
| cpa-multi-plugins | **非测试 .go 169 个 / 测试 .go 145 个** | 每条渠道一个自包含 c-shared 插件，**测试密集**，协议是逆向出来的资产 |
| workbuddy-bridge-0.1.2-source | 2331 行 / 10 文件 / **仅 2 个测试文件（共 275 行）** | 模块边界范本，但**测试很薄** |
| dsh-cpa-panel | index.js 1017 + client.js 1111 + adapters.js 313；**package.json 无 scripts、无 devDeps、零测试** | 能跑但无工程化护栏的手写 JS |
| dsh-workbuddy-bridge | **34 个 spec** + tsdown 双配置 + vitest 双 project + eslint flat | DSH 插件工程化的现成模板 |

**核心判断（全文收敛点）**：真正需要"重写"的只有 **dsh-cpa-panel 的工程化层（B/C 混合，照 dsh-workbuddy-bridge 模板 TS 化）**；CPA 宿主与 cpa-multi-plugins 应走 **A 最小裁剪**——因为它们是"测试资产 + 逆向协议资产"密集的代码，C 重写会一次性丢掉 **906 个测试文件**并重新暴露协议逆向风险。

## 1. 架构视角

### 结论
CPA 的模块边界**总体清晰、依赖方向基本单向**，且提供了一个**干净的插件扩展点**；赘肉集中在"与面板/中转无关、已被目录隔开"的外围模块（TUI/WebRTC/Home/Postgres/mDNS），删除时唯一的隐性牵连是 `main.go:38` 的匿名 import 链与 `sdk/cliproxy/auth.Manager` 向下牵出的 translator/executor。workbuddy-bridge-0.1.2-source 的模块划分好就好在**把"上游 wire 事实"与"C ABI 胶水"彻底切开**——这正是 cpa-multi-plugins 各插件目前混在一个 .so 里所欠缺的。

### 文件级证据
1. **扩展点是干净的（插件自注册）**：插件经 dlopen 后通过 `plugin.register` 自报 auth provider / executor / quota provider / 管理路由（`internal/pluginhost/management.go:39-100`、`sdk/pluginabi/types.go:36-112` 的方法表）。加一个渠道 = 放一个 .dll + `plugins.configs.<id>.enabled:true`，宿主代码零改动——这是教科书式的开闭原则。
2. **唯一硬耦合是匿名 import**：`cmd/server/main.go:38` 一行 `_ "...internal/translator"`。删 translator 子包必须同步删此 import，否则编译失败（中转最小服务报告 §2.3 已点名）。这说明"加供应商"靠**编译期注册**，而非运行期插件化——内置供应商路径与插件路径是**两套并行机制**，架构上是一个历史分层痕迹。
3. **sdk/pluginabi 与 internal/pluginhost 方向正确**：`sdk/pluginabi` 只放 ABI 契约（`ABIVersion=1`、方法名常量），`internal/pluginhost` 是加载/派发实现；插件侧只依赖 `sdk/pluginabi`，不反向 import host。依赖单向，契约与实现分离——这点是好的。
4. **workbuddy-bridge-0.1.2 的"好"可被点名**：`wire.go:7-9` 自述 *"This file is pure: no C ABI, no host calls — everything here is unit-testable"*，上游协议（`/v2/chat/completions` OpenAI 形状 SSE）集中在一个 322 行纯文件；而 `plugin.go` 只装 C ABI 胶水（顶部 cgo `cliproxy_host_api`/`cliproxy_plugin_api` 结构体）。对比 cpa-multi-plugins：一个 .so 把 wire + 签名 + 调度器 + 签到 + panel.html 全编进去，无法按函数裁剪（插件集中转报告 §3.2：`go build -buildmode=c-shared` 粒度=整插件目录）。

### 对方案选择的启示
**倾向 A（最小裁剪）为主，局部借 C 的边界思路。**
- CPA 宿主：边界已经够好，赘肉是"目录级可删"而非"需要重分层"，**B 模块重组对宿主收益很低**（它已经是 internal/sdk 两层）。删模块即可，不必重写。
- 插件集：A（整 .so 保留，配置关调度器）是成本最低路径；仅当某渠道确需瘦身时，才借鉴 workbuddy 的"wire 纯函数 + ABI 胶水"边界做**裁剪式重写**（干净重写评估已逐渠道判定：zcode 可重写、trae Intl / qoder 应保留原 dll）。

## 2. 安全视角

### 结论
CPA 的**在线鉴权姿势是合格的**（bcrypt + 常量时间比较 + 失败限流 + 远程默认关）；真正的安全短板不在"谁能调"，而在**配置与账号文件的落盘不是原子写**——崩溃/掉电可能截断 `config.yaml`。dsh-cpa-panel"密钥只在宿主半端"的说法**成立且有代码注释背书**；面板默认绑 `127.0.0.1`，只要配置正确就不暴露网络。

### 文件级证据
1. **危险端点暴露面 = v0 的历史债**：`internal/api/server_management.go` 注册了 **144 条**路由（338 行），`server_management_v8.go` 仅 **37 条**（63 行）。v0 里 `GET/DELETE /v0/management/auth-files*`、`POST credentials`（上传含上游 token 的账号 JSON）、`PUT/PATCH /v0/management/config*`（约 90 条全局配置三元组）都是"拿到管理密钥即等于拿到全部上游账号"的高危面。好在它们整体挂在同一把管理密钥后。
2. **鉴权本身做得对**：`handler.go:390` `bcrypt.CompareHashAndPassword`、`:378/:385` `subtle.ConstantTimeCompare` 比对本地/环境密钥、`:342-355` 按 IP 失败计数限流封禁（`maxFailures`/`banDuration`）、`:338` `if !localClient && !allowRemote → 403 "remote management disabled"`（**远程访问默认关**）。管理密钥为空时整组 Management API 不注册（server.go:243）。
3. **配置/账号落盘非原子（要修正前报告"原子覆盖"的说法）**：
   - `internal/config/config_yaml.go:102` `os.WriteFile(configFile, data, 0600)`——**直接原地覆盖，无 temp+rename**；
   - `internal/api/handlers/management/auth_files_crud.go:272` `os.WriteFile(dst, data, 0o600)`——同样直接写；
   - 并发保护只有**进程内互斥锁** `h.mu.Lock()`（`handler.go:402`），**没有跨进程文件锁**。权限 0600 是对的，但写中途崩溃会留下半截 YAML / 半截账号 JSON，下次 watcher 热加载可能解析失败。
4. **dsh-cpa-panel 密钥边界成立**：`client.js:11` 注释自述 *"铁律：管理密钥永远不进这一侧。所有数据都经宿主半边的 /api/v1/cpa/* 取"*；浏览器半端所有 fetch 走同源相对路径（`client.js:179` `fetch(path,{credentials:'include'})`，无 `Authorization` 头）；`client.js:930` 出现的 `http://127.0.0.1:port/management.html` 只是一个 `<a href>` 链接，不是鉴权请求。密钥只在宿主半端 `index.js:234-246 resolveAdminKey` 解析后注入 `authorization: Bearer` 头。

### 对方案选择的启示
**A 最小裁剪的同时，必须补一个小补丁（不构成重写理由）。**
- 原子写缺失是 **A 的必改项**而非 C 的理由：只需把 `config_yaml.go:102` 与 `auth_files_crud.go:272` 两处改成"写临时文件 + rename"，照搬 dsh-workbuddy-bridge 已用的 `writeFileAtomic` 模式（其 §3.1）。改动 < 30 行，不值得为此重写。
- 危险端点收敛：A 裁剪时**顺势删掉 v0 的 ~90 条配置三元组**，只留 v8 + 插件自报路由，暴露面自然收窄。B/C 都不如 A 在这一点上直接。

## 3. 可维护性 / 可测试性视角

### 结论
**这是对方案影响最大的一个视角。** CPA（761 测试文件）与 cpa-multi-plugins（145 测试文件）是**测试密集的资产**，重写等于清零这 906 个测试；而 clean 范本 workbuddy-bridge-0.1.2-source **恰恰测试很薄**（2331 行只有 275 行测试），不能因"它干净"就误以为"它被验证过"。真正缺工程化护栏的是 **dsh-cpa-panel：零 scripts、零测试、手写 CJS bundle**。

### 文件级证据
1. **CPA 测试投资惊人且集中在核心**：实测 `find -name '*_test.go'` = **761 个**，非测试 = 735 个（测试:源码 ≈ 1:1）。分布：`internal/runtime/executor` 114、`sdk/cliproxy/auth` 108、`executor/helps` 55、`handlers/management` 47、`internal/config` 35、`internal/pluginhost` 28。即——**要删的赘肉（TUI/WebRTC/postgres）和被测的核心（auth manager/selector/config/pluginhost）是分开的**。删赘肉不会烧掉核心测试。
2. **cpa-multi-plugins 同样测试密集**：145 个测试文件，workbuddy 55（`billing_401_test`/`growth_contract_test`/`redact_test`…）、trae 45（`sse_test`/`oauth_callback_test`/`credential_parity_test`…）、qoder 38（`stream_envelope_guard_test`/`checkin_campaign_test`…）、zcode 10（`signing_test`/`claim_test`…）。这些测试锁住的是**从上游逆向出来的边界行为**（信封解包、限流形状、错误码），重写后这些边界需要重新踩坑。
3. **clean 范本的"干净"≠"被验证"**：workbuddy-bridge-0.1.2-source 全仓仅 `catalog_test.go`(98) + `wire_test.go`(177) = 275 行测试，覆盖 wire/catalog 两块；`executor.go`(418)、`management.go`(240)、`plugin.go`(338) **无直接单测**。它是"模块边界好"的范本，不是"回归安全"的范本。
4. **dsh-cpa-panel 的工程化空白坐实**：`package.json` 里**根本没有 `"scripts"` 键**，无 `devDependencies`，无任何 `*.test.*`；宿主半端（index.js/adapters.js）是裸 ESM，浏览器半端 client.js 是手写 `window.__ModuleLoader__.load({factory})` CJS bundle。对照 dsh-workbuddy-bridge：**34 个 spec + vitest 双 project + tsdown 双配置 + eslint flat + coverage 阈值（lines 70/branches 60）**——这才是该插件应有的护栏现状。

### 对方案选择的启示
**强烈反对对 CPA/插件集做 C clean 重写；支持对 dsh-cpa-panel 做 B/C 工程化升级。**
- CPA + 插件集：A。它们的可维护性主要问题是"赘肉模块多"，而**核心是被 906 个测试守住的**；C 重写会让逆向协议边界失去回归保护。B（重分层）对它们收益同样不大——分层已经在。
- dsh-cpa-panel：这是唯一真正适合"照模板重来"的对象。照 dsh-workbuddy-bridge 的 tsdown+vitest+双 tsconfig 模板做 TS 化（宿主半端 index.ts/adapters.ts），既补护栏又不动已验证的 HTTP 契约（16 条调用清单）。

## 4. 性能 / 资源视角

### 结论
瘦身后宿主本身**不是性能瓶颈**：Go 静态 exe 启动快、内存 footprint 小，并发模型（gin + per-request goroutine + channel 流式转发）合理、流式无全量缓冲。**真正的资源成本在插件侧**——每个 c-shared .dll 内嵌一份独立 Go runtime，N 个插件 = N 套 runtime 驻留同一进程；插件 RPC 每方法一次 `json.Marshal/Unmarshal` 跨界，量级可忽略但确实存在。Windows 加载靠 shadow-copy + LoadLibrary，一次性成本。

### 文件级证据
1. **并发模型合理、流式无冗余缓冲**：`handlers_stream.go:605-614` 起 `dataChan := make(chan []byte)` + `errChan` + 一个 goroutine 逐 chunk 读出后经 SSE 写回，`defer close(dataChan)`——是**逐帧 channel 透传**，没有 `io.ReadAll` 把整条流读进内存。gin 每请求一 goroutine，符合 Go 惯例。
2. **插件 RPC 每请求有 JSON 序列化跨界**：进程内同地址空间（非子进程），但每次方法调用都是 `结构体 → json.Marshal → C byte buffer → 插件 → C byte buffer → json.Unmarshal`（`auth_callbacks.go` 内十余处 `json.Unmarshal(request,&...)`、`adapters_executors.go:1072` `json.Marshal(auth.Metadata)`）。单次开销是微秒级 JSON，对"一次 chat 转发"可忽略；**不是要优化的点**。
3. **c-shared 插件 = 每插件一套 Go runtime（真正的内存成本）**：每个插件是独立 go.mod 用 `go build -buildmode=c-shared`（插件集报告 §1.1），.dll 内打包各自的 Go runtime。宿主扫到几个 `.dll` 就 dlopen 几个（`internal/pluginhost/platform.go:114 selectPluginFiles`）。粗算每个插件 runtime 驻留 RSS 约 15–30MB，5 个渠道 ≈ 75–150MB 额外——**这才是瘦身后进程内存的大头，不是宿主代码量**。
4. **Windows 加载一次性成本**：`loader_windows.go:128` 先把 .dll shadow-copy 到 `%TEMP%\cliproxy-pluginhost\pid-<pid>\` 再 `LoadLibrary`（规避 Windows 不允许覆盖已映射 DLL），进程退出即清（`:193/:362`）。启动时 N 次 LoadLibrary + Go runtime 初始化是一次性秒级内成本，之后稳态无影响。宿主冷启动本身（Go runtime + gin）约几十~百毫秒量级。

### 对方案选择的启示
**性能维度不构成任何方案切换的理由。**
- A 裁剪掉 WebRTC/TUI/postgres 后，宿主 exe 体积与内存自然下降；**想进一步省内存，最高杠杆不是重写宿主，而是"只往 plugins/ 放用户实际渠道的 .dll"**（宿主扫不到就不加载，插件集报告 §3.2）——这是 A 的免费收益。
- C 重写宿主在性能上毫无收益（goroutine 流式模型已经是对的）。结论：**性能上 A 最优且零风险**。

## 5. 现代化视角

### 结论
CPA 的 **Go 语言层面其实已经现代化**（go 1.26、errors.Is/As 用得很足），最大的"陈旧点"是**日志库仍锁死 logrus（260 文件、0 处 slog）**，外加 v0/v8 双轨 API 债。JS 侧才是真正的工程化洼地：dsh-cpa-panel 无构建链无测试，cpa-multi-plugins 的 build 脚本形态陈旧且与 CI 不一致。

### 文件级证据（陈旧但可现代化清单）
1. **日志库迁移是最大的机械性现代化点**：实测 `logrus` 出现在 **260 个文件**，`log/slog` **0 处**，`zap` 0 处。Go 1.21+ 标准库 slog 已足够，迁移是"机械替换 logger 调用"而非架构改动——但 260 文件规模决定它是**可选的、非必须的**现代化，不应阻塞瘦身。
2. **错误处理其实已现代**：`errors.Is/As` 出现在 **161 个文件**，`errors.Join` 14 个；`yaml.v3 v3.0.1` 是当前主版本。说明 CPA 不是"老 Go 写法"，只是日志没跟上。
3. **v0/v8 双轨 API 债**：v0 仍有 **144 条**路由（`server_management.go`），v8 37 条（`server_management_v8.go`），且插件路由仍挂在 v0 前缀下（`/v0/management/plugins/*`）。这是向后兼容的历史包袱——A 裁剪时删 v0 冗余配置三元组即可一并还掉。
4. **JS 工程化洼地对照**：
   - dsh-cpa-panel：`"type":"module"` 但**无 scripts、无 tsconfig、无 bundler**；client.js 是手写 `__ModuleLoader__` CJS bundle。
   - dsh-workbuddy-bridge 展示了现代答案：`tsdown.config.ts` 双配置，浏览器半边用 `banner/intro/footer` **精确复现 `__ModuleLoader__.load({factory})` 包装**（而非手写），配合 vitest/eslint。
   - cpa-multi-plugins：`scripts/build.sh:18` 本地清单只编 `workbuddy qoder trae` 三个，而 CI `release.yml:108` 编五个（含 zcode/mimo）——**脚本与 CI 不一致**，是陈旧构建形态的典型。

### 对方案选择的启示
**现代化是 A 的"附加项"，不是选 C 的理由。**
- CPA：现代化点（logrus→slog、v0 收编）都能在 A 裁剪过程中顺手做，**不需要重写**。slog 迁移收益中、成本 260 文件，建议**排在瘦身之后**。
- dsh-cpa-panel：这是唯一"现代化=换形态"的对象，应照 dsh-workbuddy-bridge 模板做 TS 化（B/C），但注意——若按"简单配置页"把 client.js 整个删掉（配置页报告 §3.3 已论证），连 `__ModuleLoader__` 复现问题都消失，**全 TS 化反而最干净**。

## 6. 总判断：瘦身 / 重写的风险与收益

### 三方案逐仓裁定
| 仓库 | 推荐路线 | 理由（一句话） |
|---|---|---|
| CLIProxyAPI 宿主 | **A 最小裁剪** | 被测核心（auth/config/pluginhost/selector）与可删赘肉（TUI/WebRTC/Home/Postgres/mDNS）目录级分离；重写会丢 761 个测试、重新逆向无收益的转发管线 |
| cpa-multi-plugins | **A（整 .so 保留 + 配置关调度）**；zcode 可单独 C | 145 测试锁住逆向协议边界；.so 不可按函数裁剪，要瘦身只能整删某插件目录或整渠道重写 |
| dsh-cpa-panel | **B/C（照 dsh-workbuddy-bridge 模板 TS 化 + 补测试）** | 唯一真正缺护栏（零 scripts 零测试）的对象；且删 client 后全 TS 无障碍 |
| workbuddy-bridge-0.1.2-source | 仅作**边界范本**，不照搬其薄测试 | wire.go"纯函数可单测"的边界思路值得借，但它自身测试只有 275 行 |

### 风险与收益
- **A（推荐主线）收益**：保留全部 906 个测试的回归保护、保留已踩坑的逆向协议、可立即删目录级赘肉缩小 exe/内存；**成本**：需要处理 `main.go:38` 匿名 import 牵连 + 两处配置落盘改原子写（<30 行补丁）。**风险低**。
- **C（clean 重写）收益**：边界最干净、无历史包袱；**代价**：一次性清零 906 测试、trae Intl 双调用事件协议与 qoder COSY 签名需重新踩坑（干净重写评估已自判这两个应保留原 dll）。**仅对 zcode 这种"上游 OpenAI 形状 SSE、无签到任务"的渠道划算，对宿主整体不划算**。
- **B（模块重组）**：对 CPA 宿主基本是伪命题（它已是 internal/sdk 两层，边界够）；真正有意义的重组只发生在 dsh-cpa-panel（JS→TS 工程化）。
