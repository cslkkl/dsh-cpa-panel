## 0. TL;DR（压缩结论）

整个系统是一条 **「DSH 插件 UI → 插件宿主半端（Node）→ CPA HTTP → C ABI → 插件 .dll → 上游 HTTPS」** 的六层管道：

- **浏览器里的 React UI** 只跟「自家 Node 宿主半端」说话，永远拿不到 CPA adminKey、永远不碰文件。
- **Node 宿主半端**持有 adminKey、负责 spawn/守护 `cli-proxy-api.exe`，把浏览器请求翻译成 CPA 的 `/v0|v8/management` HTTP 调用。
- **CPA 宿主（Go exe）** 是一个 Gin HTTP 服务：`/v1/*` 转发面（OpenAI 形状 SSE，鉴权 `access.api-keys`）+ `/v0|v8/management` 管理面（鉴权 `Authorization: Bearer adminKey`）。
- **插件 .dll** 是 CPA 用 `LoadLibrary`/`dlopen` 拉进来的 C ABI 动态库，进程内 JSON-RPC method 分派；每个插件 = 一条上游渠道（workbuddy / qoder / trae / zcode / mimo / 独立 workbuddy-bridge）。
- **同一条 workbuddy 渠道在仓库里存在两份实现**：cpa-multi-plugins 的 `workbuddy.dll`（provider=`workbuddy`，带签到/任务/调度器）与 `workbuddy-bridge-0.1.2-source` 干净范本（provider=`workbuddy-bridge`，纯转发、无调度），二者 provider id 不同、auth 文件不同，可并存做 A/B。

    void   (*free_buffer)(void*, size_t);

## 4. 按代码为准修正的已知不一致

### 4.1 workbuddy-bridge-0.1.2-source 的 provider id：注释说 `workbuddy-ai`，代码是 `workbuddy-bridge`

| 位置 | 写了什么 | 性质 |
|---|---|---|
| `go.mod` 第 1 行 | `module workbuddy-ai` | Go module 名（仅构建期，不影响运行时 provider id） |
| `plugin.go:1-2` 文件头注释 | "workbuddy-ai — CLIProxyAPI plugin serving the INTERNATIONAL WorkBuddy product …" | 注释 |
| `plugin.go:10-11` 文件头注释 | "it owns `workbuddy-ai-*` auth files … and exposes itself as provider `workbuddy-ai` for A/B comparison" | **注释与代码不符** |
| **`plugin.go:75` 常量** | **`providerName = "workbuddy-bridge"`** | **代码事实（以此为准）** |
| `plugin.go:71-74` 行内注释 | "workbuddy-bridge names the dsh-workbuddy-bridge origin of this port while staying clearly distinct from the cpa-multi-plugins 'workbuddy' plugin" | 行内注释解释了为什么叫这个名 |

**结论**：CPA 面板里看到的 provider id = **`workbuddy-bridge`**（不是 `workbuddy-ai`）；auth 文件前缀也需以 `plugin.register` 实际返回的 `auth.identifier` 为准（注释声称 `workbuddy-ai-*.json`，但建议跑一次后以 `GET /v8/management/credentials` 实际文件名为最终准）。module 名 `workbuddy-ai` 是历史遗留，不影响运行时。

### 4.2 go.mod 钉 SDK v7.2.30（不是 v8）

`workbuddy-bridge-0.1.2-source/go.mod`：
```
module workbuddy-ai
go 1.26.0
require github.com/router-for-me/CLIProxyAPI/v7 v7.2.30
```

即：这个 clean 范本 against 的是 **CPA v7 SDK**，而本项目宿主 `CLIProxyAPI` 仓库是 **v8 module（`.../v8`，基于上游 v8.0.7）**。C ABI v1（`ABIVersion=1`）在 v7/v8 间保持兼容是 `sdk/pluginabi` 的承诺——`plugin.go:95` 回写 `pluginabi.ABIVersion`，宿主 `loader_unix.go:162` 校验 ABI 版本。**使用前必须实测一条插件请求冒烟**，确认 v7 SDK 编出的 .dll 能被 v8 宿主 dlopen 成功；若 ABI 不匹配，需把 go.mod 升到 `github.com/router-for-me/CLIProxyAPI/v8` 对应版本重编。

### 4.3 dsh-cpa-panel 的 peer 依赖形态

`package.json` 实证：
- **无 `"dependencies"` 字段**（完全不打包运行时依赖）。
- **仅两个 `peerDependencies`**：`@deepseek-ai/dsh-credentials >=0.1.7-rc.2`、`@deepseek-ai/schemastery ^3.18.4`。
- **`@deepseek-ai/cordis` 本身不在 peerDependencies 里**——它由 DSH 宿主运行时隐式提供（宿主 fork `@deepseek-ai/cordis@4.0.4`）。这与 dsh-workbuddy-bridge 把 `@deepseek-ai/cordis: ^4.0.4` 显式列进 peerDependencies 的做法不同（后者是 TS 工程范本，需要 cordis 类型做 typecheck）。
- 浏览器半端 `require('react')` / `require('@deepseek-ai/dsh-client-ui-primitives')` 由宿主 `PLATFORM_MODULES` 冻结注入，既不在 dependencies 也不在 peerDependencies——这是 DSH 浏览器加载器的隐式契约。

### 4.4 cpa-multi-plugins 与 workbuddy-bridge-0.1.2-source 的 workbuddy 渠道并存关系

| 维度 | cpa-multi-plugins `plugins/workbuddy/` | workbuddy-bridge-0.1.2-source |
|---|---|---|
| provider id（代码为准） | **`workbuddy`**（`plugins/workbuddy/main.go:79`） | **`workbuddy-bridge`**（`plugin.go:75`） |
| 覆盖 realm | CN（copilot.tencent.com）+ Global（workbuddy.ai）+ Intl（codebuddy.ai）三 realm 合一 | **仅 Global**（文件头 `:1-2` 自述 region=global / workbuddy.ai） |
| auth 文件前缀 | `workbuddy-<uid>.json` / `workbuddy-intl-<uid>.json`（收养 legacy `codebuddy-cn-*`） | 注释称 `workbuddy-ai-*.json`（以运行时 `auth.identifier` 为准） |
| 签到/任务 | ✅ `checkin.go` + `taskcenter.go`，后台 `go schedulerLoop` 默认开 | ❌ 全仓无 scheduler/checkin 文件 |
| 余额 | ✅ `billing.go` `/v2/billing/meter/get-user-resource` | ✅ `billing.go` 65 行（精简版） |
| Chat 转发 | OpenAI 兼容 `POST copilot.tencent.com/v2/chat/completions`，强制 stream | OpenAI 形状透传 `POST /v2/chat/completions`（`wire.go` 纯函数） |
| 模型目录 | 双路 `/v3/config` 探测（`models.go`） | 同款 `/v3/config` 远程探测一次后缓存（`catalog.go` 222 行） |
| 代码规模 | 整个 cpa-multi-plugins 仓库数万行（5 插件合一） | 2331 行 / 10 文件 |
| 加载方式 | 同 C ABI v1，产出 `workbuddy.dll` | 同 C ABI v1，产出 `workbuddy-bridge.dll` |

**并存结论**：两者**可以同时放进 CPA 的 `plugins/` 目录并存加载**——provider id 不同、auth 文件不同、`plugin.register` 时各自声明自己的 auth provider，CPA 按 auth 文件归属路由。文件头 `:9-11` 明确说这是「for A/B comparison」的 deliberate design。差异本质：cpa-multi 的 workbuddy.dll 是**全功能运营版**（带签到/任务/调度器/三 realm），workbuddy-bridge.dll 是**干净转发版**（无运营包袱，适合纯中转）。
