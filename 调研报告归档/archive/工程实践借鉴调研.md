## 背景：方案形态与术语对齐

- **CPA（Go）= 数据面**：在用户 Windows 单机上跑的中转服务，真正转发模型请求；监听本机回环；由 DSH 插件拉起 / 停止。
- **dsh-cpa-panel（TS Cordis 插件）= 控制面**：在 DSH 宿主内运行，提供配置页、启停 CPA、展示 CPA 状态；本身不转发业务流量。
- DSH（DeepSeek Harness）基于 Cordis（`@deepseek-ai/cordis` v4），插件即服务、注册即可逆 effect：DSH 官方架构说明明确"插件贡献服务、类型化事件与可逆 effect，注册在卸载时 unwind"。
  - https://github.com/deepseek-ai/deepseek-harness/blob/HEAD/docs/architecture.md
- 存在一份社区正式规范 **DSH Plugin Standard v2.0.0（2026-08-19 Adopted）**，对宿主插件、子进程、HTTP 默认安全、原子写入有硬性 MUST 条款，本方案直接对齐。
  - https://github.com/lanbaolu/dsh-plugin-standard/blob/HEAD/STANDARD.en.md

## 一、现代 Go 服务架构最佳实践（落到 CPA 瘦身）

### 1.1 配置热加载（fsnotify / reload 模式）

- **标准做法**：用 `fsnotify` 监听**父目录**（而非文件本身，因为编辑器保存常是"写临时文件 + rename"），对事件做**防抖 coalesce**（50ms 内多次保存合并成一次），回调里"读文件 → 解析 → 校验 → 原子替换"配置；校验失败则保留旧配置并记日志，不要让坏配置生效。
  - https://www.gofaq.org/en/how-to-implement-configuration-hot-reload-in-go/
  - https://www.gofaq.org/en/how-to-watch-for-file-changes-in-go/
- **监听父目录 + 处理 Create/Remove（symlink 替换）** 是 K8s ConfigMap 热加载在 Go 里的同款模式，对单机配置文件同样适用。
  - https://kubernetes.unisbadri.com/en/configuration-and-secret/configuration-hot-reload/
- **对 CPA 的落地**：配置由插件侧写盘（插件是配置 owner），CPA 用 fsnotify 监听该文件，校验失败回滚旧值；不需要 K8s informer 那种重型方案。

### 1.2 优雅停机（signal.NotifyContext + HTTP Shutdown）

- **标准两段式**：`signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)` 拿到 stopCtx；`<-stopCtx.Done()` 后用**带超时的 context**（如 5–30s）调 `srv.Shutdown(ctx)`——它先停 listener、关 idle 连接、等在途请求结束，超时则中止。
  - https://nalar.dev/graceful-http-server-shutdown-in-go/
  - https://wawand.co/blog/posts/graceful-shutdown-patterns-in-go/
  - https://bytelearn.dev/go-in-practice/graceful-shutdown
- **坑（重要）**：`http.Server.Shutdown` **不会等待 WebSocket / hijacked 连接**，这类长连接必须自行跟踪并在停机时显式关闭。
  - https://alivedise.github.io/backend-engineering-essentials/distributed-systems/graceful-shutdown-and-connection-draining
- **Windows 注意**：`os.Interrupt`（Ctrl+C）+ 任务结束信号即可；CPA 作为被插件拉起的子进程，停机主要靠插件 disposer 给它发信号 / kill，而不是靠控制台 Ctrl+C。

### 1.3 进程生命周期与监督（Windows 子进程、崩溃重启、就绪探针）

**(a) CPA 自身作为服务进程的生命周期**
- 用 `signal.NotifyContext` 统一取消一切 goroutine；停机顺序与 1.2 一致。

**(b) 插件侧托管 CPA 子进程（Windows 专属）**
- **父进程退出时不留下孤儿**：Windows 没有 Linux 的 `Pdeathsig` 等价物，标准解法是 **Job Object + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`**——用 `golang.org/x/sys/windows` 的 `CreateJobObjectW` / `AssignProcessToJobObject` / `TerminateJobObject`，把 CPA 进程（及其后代）加入 Job，Job 句柄随父退出关闭时整棵进程树自动被杀。
  - https://go.dev/src/cmd/vendor/golang.org/x/sys/windows/syscall_windows.go
  - https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects
  - https://juejin.cn/post/7546479364020748340 （中文：Windows 下用 Job Object 实现父退子亡）
- **兜底**：`taskkill /PID <pid> /T /F`（`/T` 连子进程树一起结束）。
  - https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/taskkill
- **不要用 shell 拼命令字符串**：DSH Plugin Standard §3.6.1 硬性要求"non-shell `spawn`、固定参数数组、无 shell 字符串拼接"（防注入）；子进程必须有超时、exit/error 监听、kill 兜底、可取消，禁止孤儿。
  - https://github.com/lanbaolu/dsh-plugin-standard/blob/HEAD/STANDARD.en.md

**(c) 崩溃自动重启（mini supervisor）**
- 社区模式：子进程退出即重启，但加**指数退避 + jitter**；若启动后 5s 内就崩则倍增延迟，若稳定运行超过 30s 则重置退避；并设"时间窗内最大重启次数"（如 60s 内 10 次）防止崩溃循环把宿主拖死。
  - https://karandeepsingh.ca/posts/devops-trends-2026/amp
- DSH 生态对应红线：DSH Plugin Standard 附录第 9 条"坏插件自愈必须带 backoff，绝不能造成宿主启动崩溃循环，验证通过后才持久化"。
  - https://github.com/lanbaolu/dsh-plugin-standard/blob/HEAD/STANDARD.en.md

**(d) 就绪探针（readiness）**
- 插件拉起 CPA 后，**轮询 CPA 的 `/readyz` 直到就绪**，再认为"托管成功"并点亮配置页状态；不要只看进程已退出码 0 就算成功。
  - 探针语义见 1.6。

### 1.4 插件 / 动态加载三种路线对比

| 路线 | 适用 | 坑 | 对 CPA 的结论 |
|---|---|---|---|
| **Go `plugin` 包** | Linux/macOS 动态 `.so` | **不支持 Windows**；不能 unload；宿主与插件必须同 Go 版本/同依赖编译；加载后无法替换 | **不需要** |
| **c-shared + `dlopen`** | CGO 出 `.so` 动态加载 | 强依赖 CGO；Windows 上 dll 加载/符号/路径坑多；同样难卸载 | **不需要** |
| **WASM（wazero / Extism / TinyGo）** | 不可信插件沙箱、跨语言 | Go 生态里只能用 TinyGo；无内置并发；GC runtime 使二进制偏大；WASI 能力一经授予插件即全量可达 | **不需要** |

- 证据：
  - Go plugin 仅 Linux/BSD/macOS、基于 dlopen、不能卸载/替换、需 CGO：https://crg.eti.br/pt-br/post/go-plugins/
  - eKuiper 对 Go plugin 的实战吐槽（仅三平台、插件不可关闭、必须同版本编译）：https://ekuiper.org/docs/en/v1.12/extension/overview.html
  - WASM 插件沙箱边界与"授权即全量"风险：https://www.systemshardening.com/articles/wasm/wasm-platform-extension-security/
  - WASM 服务端现实坑（TinyGo、GC 二进制大、系统调用移植成本）：https://novvista.com/webassembly-beyond-the-browser-server-side-wasm-in-practice/
  - APISIX 的 Wasm 实践（Go 只能 TinyGo、缺并发、栈不成熟）：https://apisix.apache.org/blog/2023/07/07/tiny-apisix-plugin/
- **结论**：CPA 是**被插件托管的独立单体进程**，动态性由"拉起/重启/换二进制进程"实现，**不在 CPA 内部再做插件 ABI**。这与 DSH"一切皆插件"的分层互补——扩展点在 TS 插件侧，不在 Go 侧。

### 1.5 管理端点安全默认

- **默认绑回环 `127.0.0.1`，不要绑 `0.0.0.0`**：pprof / metrics / debug / admin 这类管理面只本机可达是社区 SCA 规则的安全写法。
  - https://docs.cli.vulnetix.com/docs/sast-rules/vnx-go-019/
- **同类项目的一致默认**：Kong Admin API 绑 `127.0.0.1:8001` + 鉴权；APISIX `allow_admin: 127.0.0.0/24`；OpenHive/openbucket 等单机 agent 一律"loopback-only、强 admin key、绝不 `*` 远程管理"。
  - https://www.invicti.com/web-application-vulnerabilities/unprotected-kong-gateway-admin-api-interface
  - https://apisix.apache.org/blog/2023/02/09/secure-apisix-admin/
  - https://github.com/alexngai/openhive/blob/HEAD/docs/reference/security.md
  - https://github.com/Razin-developer/openbucket/blob/HEAD/docs/SECURITY.md
- **DSH 硬性默认（P4）**：每个本机 HTTP 端点必须校验 **loopback + Host + Origin/Sec-Fetch-Site**、限制 body 大小、不泄漏内部错误；特权操作需鉴权 + 确认 + 回滚。
  - https://github.com/lanbaolu/dsh-plugin-standard/blob/HEAD/STANDARD.en.md
- **密钥 / token 存储**：不设默认口令；CPA 启动时生成随机 admin token，通过**本机临时文件或启动握手**交给插件侧（参考随机 hex 生成），令牌不出本机、不进 UI 原文。
  - https://www.jetbrains.com/guide/go/tutorials/authentication-for-go-apps/auth/
- **对 CPA 的落地**：管理面（`/admin/*`、`/readyz`、`/healthz`）与数据面（模型转发端口）可同进程不同路由，但**全部绑 `127.0.0.1`**；`/admin/*` 校验一次性 bearer token。

### 1.6 结构化日志与健康检查语义

- **结构化日志**：Go 1.21+ 标准库 `log/slog`，生产用 JSON handler，带时间/级别/request id。
  - https://www.facsiaginsa.com/golang/structured-logging-metrics-and-graceful-shutdown-in-go-on-ubuntu
- **liveness vs readiness 语义（关键区分）**：
  - `/healthz`（liveness）：只答"进程活着、没死锁"，**不查任何外部依赖**，快速返回；失败=编排器该重启它。
  - `/readyz`（readiness）：答"现在能否服务流量"，查关键依赖（如上游可达），**不查可选依赖、单次 <1s**；失败=负载均衡把流量摘掉，但**不重启**。
  - https://khimananda.com/blog/graceful-shutdown-and-health-checks-in-go
  - https://web-alert.io/blog/health-check-endpoint-design-livez-readyz-guide
- **停机期间语义**：开始优雅停机时**先把 readiness 翻成 not-ready**（摘流量），liveness 仍保持，让在途请求跑完。
  - https://khimananda.com/blog/graceful-shutdown-and-health-checks-in-go
- **原子就绪标志**：用 `atomic.Bool` 翻 readiness，handler 读标志即可，无需锁。
  - https://www.gofaq.org/en/how-to-implement-health-check-endpoints-in-go/

### 一节清单：照搬 / 参考 / 不需要

**照搬（CPA 直接用）**
- fsnotify 监听**父目录** + 防抖 + 读-解析-校验-原子替换，坏配置回滚旧值。
- `signal.NotifyContext` + `srv.Shutdown(带超时 ctx)`；停机先翻 readiness。
- Windows 用 **Job Object + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`** 保证父退子亡，`taskkill /T /F` 兜底；非 shell spawn、固定参数数组。
- 崩溃重启带**指数退避 + jitter + 时间窗最大重启次数**，防崩溃循环。
- 管理面与数据面**全绑 `127.0.0.1`**；`/admin/*` 校验随机 bearer token；校验 loopback/Host/Origin/Sec-Fetch-Site、限 body。
- `slog` JSON 日志；`/healthz`（不查依赖）+ `/readyz`（查关键依赖、<1s、atomic.Bool）。

**参考（按需裁剪）**
- 长连接（若 CPA 走 SSE/WebSocket 流式转发）必须自行跟踪连接并在 Shutdown 时显式关闭——`http.Server.Shutdown` 不管它们。
- 就绪探针：插件侧轮询 `/readyz` 成功才算"托管完成"。

**不需要**
- Go `plugin` 包（不支持 Windows、不可卸载）。
- c-shared/dlopen（CGO、Windows 坑多）。
- 在 CPA 内部嵌 WASM 插件运行时（TinyGo、无并发、GC 二进制大）——动态性交给进程托管。
- K8s informer / Hash 注解 / Spring Refresh 这类集群级热加载方案。

## 二、DSH / Cordis 插件 TS 工程实践（落到 dsh-cpa-panel）

### 2.1 TS 工程化栈（tsdown / tsx / vitest / eslint）

- **tsdown**（Rolldown 系，与 Vite 同团队）是 2025–2026 写 TS 库的主流打包器：`entry` + `outDir` + `format:["esm"]` + `dts:true`，一次产出 ESM 与类型声明。
  - https://viblo.asia/p/cach-viet-mot-thu-vien-javascript-voi-vite-tsdown-rolldown-pnpm-2vJPdWqqJeK
- **运行/测试**：后端 TS 运行事实标准是 `tsx`，与 Vitest 天然衔接；`"test": "vitest run"`（CI 一次性）+ watch 模式本地。
  - https://quadcube.tistory.com/m/274
  - https://docs.luanroger.dev/ts-package-template/docs/overview
- **对 dsh-cpa-panel 的落地**：直接对齐参考工程 `dsh-workbuddy-bridge` 的栈——tsdown 打 `lib/`、vitest 单测、eslint（typescript-eslint v8 + eslint-config-prettier）、prettier、双 tsconfig（server/client）、`"check": "typecheck && build && test"`。这也是 DSH Plugin Standard §6.1 的硬性要求（`typecheck/build/test/verify/pack` 脚本齐全、CI 跑全套 + `npm audit` + `npm pack --dry-run`）。
  - https://github.com/lanbaolu/dsh-plugin-standard/blob/HEAD/STANDARD.en.md

### 2.2 schemastery schema 驱动配置页

- DSH/Cordis 用 `@deepseek-ai/schemastery`（Koishi 同源）写插件 `Config`：**默认值直接写在 schema 里**，`Schema.number().default(0).min(0).max(100).step(1)`、`Schema.object({...})`、`Schema.boolean()`，UI 由 schema 自动生成。
  - DSH 插件配置示例：https://web-tutorial.com/deepseek-harness/config.html
  - Koishi 插件用 `Schema.number().description().default()` 驱动校验 + UI 的实例：https://deepwiki.com/koishijs/koishi-plugin-mediawiki/6.1-configuration-schema
- **DSH 硬性要求（§3.1.1）**：函数插件导出 `name/inject/Config/apply`，`Config` 用 schemastery 且默认值在 schema 内。
  - https://github.com/lanbaolu/dsh-plugin-standard/blob/HEAD/STANDARD.en.md
- **落地**：CPA 的监听端口、上游地址、自动重启开关、日志级别等都做成 schema 字段；配置页（自定义 tabs UI）与 schema 同源，不要手写两套表单逻辑。

### 2.3 Cordis 生命周期（apply / start / stop / dispose）

- **官方模型**：`ctx.plugin()` 返回 Fork，调 `fork.dispose()` 运行时停用插件；一切副作用应可在 dispose 时反转。
  - https://cordis.moe/zh-CN/guide/essential/lifecycle.html
  - https://www.npmjs.com/package/@cordisjs/core
- **DSH 硬性资源归属（P3 / §3.2）**：路由、监听器、定时器、watcher、socket、React root、DOM、临时服务、**子进程**，全部由当前 fiber 通过 `ctx.effect(() => disposer, label)` 拥有；`ctx.on`/`host.on` 必须包在 `ctx.effect` 里或由 disposer 移除，不依赖框架隐式清理。
  - https://github.com/lanbaolu/dsh-plugin-standard/blob/HEAD/STANDARD.en.md
- **disposer 顺序（§3.2.3）**：先停外部入口 / 反注册 → 取消并等待在途工作 → 关闭资源。
  - https://github.com/lanbaolu/dsh-plugin-standard/blob/HEAD/STANDARD.en.md
- **落地**：**拉起 CPA 子进程这件事必须写在 `ctx.effect` 里**，disposer 返回的清理函数负责停 CPA（发信号 → 等优雅退出 → kill 兜底）。这样用户在 DSH 里停用/升级插件时，CPA 一定被干净回收，不会留孤儿。

### 2.4 "本地服务 / 子进程托管类插件"生态先例

- **Koishi 官方服务模式**：`ctx.puppeteer` 就是一个由插件提供、管理浏览器子进程的服务；"提供服务的插件被卸载时，其注册的服务一并移除"——这正是我们"插件托管 CPA"的同构先例。
  - https://koishi.js.org/guide/aspect/service.html
- **子进程管理硬性约束（DSH §3.6）**：非 shell spawn、固定参数数组；子进程有超时、exit/error 监听、kill 兜底；后台/缓存路径可取消；无孤儿。
  - https://github.com/lanbaolu/dsh-plugin-standard/blob/HEAD/STANDARD.en.md
- **持久化原子写（DSH §3.5.1）**：人类可读 JSON 用"同目录临时文件 + fsync + rename 原子发布"，禁止直接 `writeFileSync` 覆盖；同资源读-改-写用进程内 promise 链锁串行化。
  - https://github.com/lanbaolu/dsh-plugin-standard/blob/HEAD/STANDARD.en.md
- **参考工程自身**：`dsh-workbuddy-bridge` 已示范 DSH 插件结构、provider 注册、自定义 tabs 配置页、`exports["./client"]` + `dsh.client.platform:"web"` 的客户端契约；其 README 致谢里 `franksong2702/dsh-codex-connect` 是另一个 DSH 插件结构参照。
  - https://github.com/zlZayn/dsh-workbuddy-bridge

## 三、控制面 / 数据面架构参考（映射到我们形态）

### 3.1 可引用的参考设计

**(a) LiteLLM——最贴近的"网关 + 管理面"分层**
- 微服务拆分明确三个面：
  - **gateway :4000 = 数据面**：`/chat/completions`、`/v1/messages`、embeddings 等 LLM 实际代理 + `/health`、`/metrics`。
  - **backend :4001 = 管理面 API**：keys、users、teams、orgs、SSO、审计日志、花费/用量分析。
  - **ui :3000 = Next.js 仪表盘**。
  - https://docs.litellm.ai/docs/proxy/microservices_helm
- **HA 模式更直白**：控制面只服务 admin UI、知道所有 worker，**绝不代理/路由任何 LLM 请求**；每个 worker 是独立代理，处理本区域/本团队的真实流量。
  - https://docs.litellm.ai/docs/proxy/high_availability_control_plane

**(b) Agent Gateway——单机 localhost 绑定的最佳默认**
- admin UI 在 `http://localhost:15000/ui`，readiness 在 `localhost:15021/healthz/ready`；**admin、metrics、readiness 全部绑 localhost**。
  - https://aaif.io/blog/putting-a-front-door-on-local-ai-with-agentgateway

**(c) Nginx Proxy Manager——"面板只管配置，代理进程才跑流量"**
- Node.js 后端 + SQLite/MySQL 存代理主机/证书/规则；**真正的流量由 nginx 进程跑**，其配置由后端从数据库动态生成；Web UI 通过后端 API 改配置。
  - https://www.pistack.xyz/posts/2026-04-24-nginx-proxy-manager-vs-swag-vs-caddy-docker-proxy-self-hosted-reverse-proxy-gui-guide-2026/
  - https://byteguard.hashnode.dev/nginx-proxy-manager-vs-traefik-vs-caddy

**(d) 浏览器扩展 + 本地守护进程（Privilege Separation）**
- XrayInChrome：**低权限前端 + 高权限后端**，Go 写 Native Host、一键注册表安装，扩展与系统进程安全通信。
  - https://chromewebstore.google.com/detail/xray-in-chrome/dijagbplhpidjbefjeojdefkgflbmekj
- Chromex：Native Messaging Host（relay）+ Local Bridge（daemon，居中 host 与 app-server）三层。
  - https://b-lab.team/en/content/a03c14e9-a864-4584-bd25-c44bcd0867bb
- Native Messaging 本身：manifest 白名单允许的扩展；**host 崩溃浏览器会自动重启它**。
  - https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/native-messaging
  - https://martinuke0.github.io/posts/2026-03-31-chrome-native-messaging-building-secure-bridge-between-extensions-and-native-applications/

### 3.2 映射到本方案（DSH 插件 = 控制面，CPA = 数据面）

| 参考模式 | 参考组件 | 本方案对应 |
|---|---|---|
| LiteLLM gateway :4000 | 数据面，转发 LLM | **CPA（Go）**：监听 `127.0.0.1:<port>`，转发模型请求 |
| LiteLLM backend :4001 + ui :3000 | 管理 API + 仪表盘，不碰流量 | **dsh-cpa-panel（TS Cordis 插件）**：配置页 + 启停 CPA + 看状态 |
| LiteLLM "控制面不代理流量"原则 | control plane 与 worker 物理分离 | 插件**只**通过 loopback `/admin/*` 管理 CPA，**绝不**在 DSH 进程内转发模型流量 |
| Agent Gateway localhost 绑定 | admin/metrics/ready 全绑回环 | CPA 所有端点（数据面端口 + `/admin/*` + `/readyz`）绑 `127.0.0.1` |
| NPM 后端写 DB → 动态生成 nginx 配置 | 面板是配置 owner | 插件是配置 owner，写盘 → CPA fsnotify 热加载 |
| NPM 里 nginx 独立进程跑代理 | 数据面可独立重启/升级 | CPA 独立进程，插件 disposer 重启它即"换数据面"，不影响 DSH 宿主 |
| XrayInChrome 低权前端 + 高权 Go 后端 | 权限分离 | DSH 插件（Node，低权）↔ CPA（Go，持有上游 token、做转发） |
| Native Messaging host 崩溃自动重启 | 守护 | 插件侧 mini supervisor（退避重启 CPA） |

**核心结论**：本方案就是 LiteLLM 单机版的"控制面/数据面 + NPM 的面板管配置"组合——
- **控制面（插件）**负责：配置 schema、启停 CPA、轮询 `/readyz`、展示状态、把配置原子写盘。
- **数据面（CPA）**负责：回环端口转发、上游鉴权、`/healthz`+`/readyz`、slog 日志、被拉起/被回收。
- 两者之间只走 **loopback HTTP + 一次性随机 token**，不跨网络、不暴露端口。

## 四、汇总：最终借鉴清单

### 4.1 dsh-cpa-panel（TS / Cordis 插件）

**照搬**
1. 工具链：tsdown（ESM + d.ts）+ tsx + vitest + eslint(typescript-eslint v8) + prettier + 双 tsconfig；脚本含 `typecheck/build/test/verify/pack`，CI 全套 + `npm audit` + `npm pack --dry-run`。（[tsdown](https://viblo.asia/p/cach-viet-mot-thu-vien-javascript-voi-vite-tsdown-rolldown-pnpm-2vJPdWqqJeK)、[vitest/tsx](https://quadcube.tistory.com/m/274)、[DSH Std §6](https://github.com/lanbaolu/dsh-plugin-standard/blob/HEAD/STANDARD.en.md)）
2. 配置：`Config` 用 `@deepseek-ai/schemastery`，默认值进 schema，配置页与 schema 同源。（[DSH config](https://web-tutorial.com/deepseek-harness/config.html)、[Koishi Schema 实例](https://deepwiki.com/koishijs/koishi-plugin-mediawiki/6.1-configuration-schema)）
3. 生命周期：拉起/停止 CPA 写在 `ctx.effect(() => disposer, label)`；disposer 顺序=停入口→等在途→关资源。（[Cordis lifecycle](https://cordis.moe/zh-CN/guide/essential/lifecycle.html)、[DSH Std §3.2](https://github.com/lanbaolu/dsh-plugin-standard/blob/HEAD/STANDARD.en.md)）
4. 子进程：非 shell spawn + 固定参数数组 + 超时 + exit/error 监听 + kill 兜底，无孤儿。（[DSH Std §3.6](https://github.com/lanbaolu/dsh-plugin-standard/blob/HEAD/STANDARD.en.md)）
5. 持久化：配置落盘走"临时文件 + fsync + rename"，读-改-写用 promise 链锁。（[DSH Std §3.5](https://github.com/lanbaolu/dsh-plugin-standard/blob/HEAD/STANDARD.en.md)）
6. HTTP 安全：本机端点校验 loopback + Host + Origin/Sec-Fetch-Site、限 body、不泄漏内部错误。（[DSH Std P4](https://github.com/lanbaolu/dsh-plugin-standard/blob/HEAD/STANDARD.en.md)）

**参考**
- 把 CPA 封成可 `inject` 的 service（对标 Koishi `ctx.puppeteer`），便于将来其他插件复用。（[Koishi service](https://koishi.js.org/guide/aspect/service.html)）
- 自定义 tabs 配置页 + 状态卡（对标参考工程 `dsh-workbuddy-bridge`）。（[repo](https://github.com/zlZayn/dsh-workbuddy-bridge)）

**不需要**
- Native Messaging manifest / 浏览器扩展机制；Erlang 式监督树；tsdx 旧打包链。

### 4.2 CPA 瘦身（Go 单机中转）

**照搬**
1. 热加载：fsnotify 监听父目录 + 防抖 + 读-解析-校验-原子替换，坏配置回滚旧值。（[gofaq reload](https://www.gofaq.org/en/how-to-implement-configuration-hot-reload-in-go/)）
2. 优雅停机：`signal.NotifyContext` + `srv.Shutdown(带超时 ctx)`；停机先翻 readiness。（[nalar](https://nalar.dev/graceful-http-server-shutdown-in-go/)、[bytelearn](https://bytelearn.dev/go-in-practice/graceful-shutdown)）
3. Windows 子进程树回收：Job Object + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`（`golang.org/x/sys/windows`），`taskkill /T /F` 兜底。（[MS Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)、[juejin](https://juejin.cn/post/7546479364020748340)）
4. 崩溃重启：指数退避 + jitter + 时间窗最大重启次数，防崩溃循环。（[karandeepsingh](https://karandeepsingh.ca/posts/devops-trends-2026/amp)）
5. 安全默认：全部端点绑 `127.0.0.1`；`/admin/*` 校验随机 bearer token；不设默认口令。（[vulnetix](https://docs.cli.vulnetix.com/docs/sast-rules/vnx-go-019/)、[Kong admin](https://www.invicti.com/web-application-vulnerabilities/unprotected-kong-gateway-admin-api-interface)、[openbucket SECURITY](https://github.com/Razin-developer/openbucket/blob/HEAD/docs/SECURITY.md)）
6. 可观测：`log/slog` JSON；`/healthz`（不查依赖）+ `/readyz`（查关键依赖、<1s、`atomic.Bool`）。（[health checks](https://khimananda.com/blog/graceful-shutdown-and-health-checks-in-go)、[livez/readyz 语义](https://web-alert.io/blog/health-check-endpoint-design-livez-readyz-guide)）

**参考**
- 流式转发若走 SSE/WebSocket，需自行跟踪长连接并在 Shutdown 显式关闭（`http.Server.Shutdown` 不管它们）。（[connection draining](https://alivedise.github.io/backend-engineering-essentials/distributed-systems/graceful-shutdown-and-connection-draining)）
- 就绪探针：插件轮询 `/readyz` 成功才算托管完成。

**不需要**
- Go `plugin` 包 / c-shared+dlopen / 内嵌 WASM 运行时（CPA 内部不做插件 ABI）。
- K8s informer、Hash 注解、Spring Refresh 等集群级热加载。
- 暴露 pprof/metrics 到非回环地址；0.0.0.0 监听。
