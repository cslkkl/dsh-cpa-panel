## 2. 独立调用单元设计（新）

### 2.1 单元定义与 DSH 配置 schema
一个「单元」= `(渠道 provider, 账号 authRef, 模型 model)` 三元组，DSH 配置里声明：

```jsonc
units: [
  {
    "id": "wb-acc1-glm45",          // 单元 id
    "provider": "workbuddy",          // 渠道 provider id
    "authRef": "workbuddy-001",       // auths 账号文件 id/label
    "model": "glm-4.5-air",           // 该单元固定模型
    "enabled": true,
    "accessKey": "sk-<per-unit>",     // 每单元一个 /v1 调用 key（见 2.3）
    "reasoningEffort": "medium"       // 该单元默认思考强度（见 §3）
  }
]
```

### 2.2 「钉死单账号」机制盘点（现有能力证据）

| 候选通道 | 现有证据 | 结论 |
|---|---|---|
| **`pinned_auth_id` metadata** | executor 常量 `PinnedAuthMetadataKey="pinned_auth_id"`（sdk/cliproxy/executor/types.go:35-36）；selector 读 `pinnedAuthIDFromMetadata`（conductor_execution.go:1698），命中后 `if pinnedAuthID!="" && auth.ID!=pinnedAuthID` 直接排除其它 auth（conductor_selection.go:1203、1295） | **原语齐全，selector 已只认该 auth**；缺一个外部写入通道 |
| `WithPinnedAuthID` | handlers_context.go:69；目前仅内部调（model_execution.go:115/151） | 现成 helper，挂到 /v1 入口即可 |
| `access.api-keys` 绑模型/账号 | config_access/provider.go:30——**只是扁平 key 集合 `map[string]struct{}`**，只做「key 在不在」校验，**不带任何 model/provider/auth 绑定** | 不能直接用 |
| ModelRouter 编码账号 | 插件 `applyModelRouter`（handlers_routing.go:325）收到 model name+headers+body，可解析 `model@authRef` 并路由到指定 auth 的 executor | 可行，纯插件侧，但要插件支持 |
| `host.auth.list/get` 回调 | management.go:191/223——插件列/取宿主账号，用于面板展示，不是转发期选号 | 仅展示，非选号通道 |

### 2.3 推荐机制（二选一，首选甲）
- **甲（推荐，宿主加约 10 行）**：access 中间件校验 key 后，DSH 侧维护 `key→unit{provider,authID,model}` 映射；宿主在入口读该映射并 `WithPinnedAuthID(ctx, authID)`（handlers.go:229-231 已在读 pinnedAuthID）。等价于「每单元一个 access key + key 绑定单元」——利用已有的 pinned 原语，selector 自动只走该 auth，**不负载均衡、不混用**。
- **乙（零宿主改动）**：模型名编码账号 `glm-4.5-air@workbuddy-001`，由 workbuddy 插件 ModelRouter 解析 authRef，插件 executor 用 `host.auth.get` 取该账号执行。DSH 调 `/v1/chat/completions` 时 model 字段填编码名。

> 单元不可用/账号禁用：pinned 到的 auth 被禁用或冷却 → selector 无候选 → 返回 `auth_not_found`/该账号冷却错误（conductor_execution.go:319），**不会自动落到同 provider 别的账号**（正是「绝不混用」要的行为）。

### 2.4 单元级调用链
```
DSH --POST /v1/chat/completions (Authorization: Bearer <单元key>, model=<单元模型>)
  → access 中间件校验 key（config_access/provider.go）
  → key→unit 映射 → WithPinnedAuthID(authID)
  → providersForExecution 解析 model→provider=workbuddy
  → conductor selector：仅 pinned auth 候选，跳过 RR/加权（conductor_selection.go:1203）
  → workbuddy 插件 executor 用该 auth 调上游
  → 流式 SSE 回传
```

## 3. executor / 思考强度契约

### 3.1 检测设计
- **有 `reasoning_effort`/`thinking`**：按渠道能力映射/透传。
  - workbuddy-bridge：已知 `reasoning_effort:"off"` 会被 GPT 系拒绝 → **需 drop 该字段或改写为合法值**（对应 wire/executor 处理）。
  - trae/qoder：按各自 wire/executor 对 thinking 的接受度映射（on/off/medium/high）。
- **无该字段**：用默认值，**不报错**。默认值来源：DSH 单元配置 `reasoningEffort`（建议默认 `medium` 或 `off`，按渠道）；缺省回落模型注册表能力。

### 3.2 实现位置
- **放在插件 executor 内**（workbuddy/bridge 的 executor.go）：因为各渠道对 thinking 的接受/拒绝规则是上游特定的，宿主不应统一改写。宿主 `internal/thinking`（suffix 解析）只做 `model(thinking suffix)` 语法识别，真正的「有→映射/透传、无→默认」在插件 executor 完成。
- DSH 侧只负责在请求体里注入/不注入 `reasoning_effort`，或在单元配置给默认值。
