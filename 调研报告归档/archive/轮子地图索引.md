## 0. 压缩结论（先看这里）

整个系统是一条六层管道：**DSH 浏览器 UI（React）→ DSH 宿主半端（Node ESM/Cordis，持 adminKey、spawn CPA）→ CPA HTTP（Go/Gin，127.0.0.1:8317）→ C ABI（进程内 LoadLibrary/dlopen）→ 插件 .dll（Go c-shared）→ 上游厂商 HTTPS**。

**轮子一句话归属**：
- **宿主数据面 = CLIProxyAPI v8 做 A 最小裁剪**（删 TUI/WebRTC/Home/Postgres/mDNS/Docker，保留 auth.Manager + pluginhost + watcher + v8 管理面 + openai 转发）；
- **五条渠道 = cpa-multi-plugins 整 .so 保留**（workbuddy/trae/qoder/zcode/mimo 按用户账号池按需投放，配置关自动调度器），workbuddy 另有 `workbuddy-bridge-0.1.2-source` 干净范本做 global A/B；
- **控制面面板 = dsh-cpa-panel 照 dsh-workbuddy-bridge 模板 TS 化**（tsdown/vitest/双 tsconfig/schemastery，顺手删 client bundle 走 schema 驱动表单）；
- **配置页字段/容错 = 外部借鉴** new-api 渠道字段表 + LiteLLM fallback/allowed_fails + OpenRouter 故障窗口。

**路线判定**：支持 **A 最小裁剪 + 局部自研补丁**（对照多视角审视报告）。CPA 宿主与插件集走 A（重写会一次丢掉 906 个测试文件 + 重新踩逆向协议坑）；唯一划算的 clean 重写是 **zcode 单渠道**（上游本就是 OpenAI 形状 SSE、无签到任务）；B 模块重组对宿主是伪命题（已是 internal/sdk 两层），真正的重组只发生在 dsh-cpa-panel 的 JS→TS 工程化层。

### 3.3 该地图支持 A / B / C 哪个选项

**支持：A 最小裁剪为主线 + 局部自研补丁；C 仅 zcode 单渠道划算。**（对照多视角审视报告结论）

- **CPA 宿主 → A**：被测核心（auth/config/pluginhost/selector，108+35+28 个测试文件）与可删赘肉（TUI/WebRTC/Home/Postgres/mDNS）目录级分离；重写会一次丢掉 **761 个宿主测试 + 145 个插件测试 = 906 个测试文件**，且重新暴露协议逆向风险。B 模块重组对宿主是伪命题（已是 internal/sdk 两层，边界够）。
- **插件集 → A（整 .so 保留 + 配置关调度器）**：.so 不可按函数裁剪，要瘦身只能整删某插件目录或整渠道重写；trae Intl 双调用事件协议与 qoder COSY 签名重写需重新踩坑，应保留原 dll。**唯一划算的 clean 重写是 zcode**（上游 OpenAI 形状 SSE、无签到任务、静态模型表，<800 行）。
- **dsh-cpa-panel → B/C（照模板 TS 化）**：这是唯一真正缺护栏（零 scripts/零测试/手写 CJS bundle）的对象；照 dsh-workbuddy-bridge 模板 TS 化即补护栏，且删 client bundle 后全 TS 无障碍，不动已验证 HTTP 契约。

**一句话收尾**：不要重写一个被 906 个测试守住、且赘肉已被目录边界隔开的系统；要重写的是那个没有任何测试护栏、连 scripts 都没有的面板插件。宿主走 A 裁剪（顺手补原子写 M3 + 收 v0 M4 + 加 shutdown M2），插件集走 A 保留（zcode 可选单独重写），面板走照模板 TS 化。
