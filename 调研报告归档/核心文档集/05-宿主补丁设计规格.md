## 1. 五处补丁（接口级，每处四要素）

> 四要素固定为：①现状代码 + 锚点行号（实测）；②改动内容；③接口签名/行为；④验证点 = 现象 / 预期 / 方法 / 通过标准。

### 补丁 1　原子写 ×3（temp + fsync + rename，失败保留旧值不写盘）

| # | 现状代码（实测锚点） |
|---|---|
| 1a | `internal/config/config_yaml.go:102` → `if err = os.WriteFile(configFile, data, 0600); err != nil { return err }` |
| 1b | `internal/api/handlers/management/auth_files_crud.go:272`（`writeAuthFile` 内）→ `if errWrite := os.WriteFile(dst, data, 0o600); errWrite != nil { ... }` |
| 1c | `internal/config/config_load.go:223`（启动时清理冲突字段回写）→ `if errWrite := os.WriteFile(configFile, cleaned, 0600); errWrite != nil { ... }` |

- **改动内容**：三处裸 `os.WriteFile` 全部替换为「写同目录临时文件 → `f.Sync()` 落盘 → `os.Rename(tmp, 目标)` 原子替换」。统一抽一个 `writeFileAtomic(path string, data []byte, perm os.FileMode) error` helper（建议落 `internal/config` 或 `internal/util`），三处复用。
  - 模板：
    ```go
    tmp := path + ".tmp"
    f, err := os.OpenFile(tmp, os.O_CREATE|os.O_WRONLY|os.O_TRUNC, perm)
    if err != nil { return err }
    if _, err := f.Write(data); err != nil { f.Close(); os.Remove(tmp); return err }
    if err := f.Sync(); err != nil { f.Close(); os.Remove(tmp); return err }
    if err := f.Close(); err != nil { os.Remove(tmp); return err }
    if err := os.Rename(tmp, path); err != nil { os.Remove(tmp); return err }
    return nil
    ```
- **接口签名/行为**：
  - helper 签名 `writeFileAtomic(path string, data []byte, perm os.FileMode) error`，对外行为与原 `os.WriteFile(path, data, perm)` 完全一致（成功 nil、失败 error），**调用点签名不变**。
  - **失败语义硬约束**：写盘任一阶段失败 → 删除 tmp、返回 error、**目标文件保持旧值不动、不热重载**（与补丁 4 的「校验失败保留旧值」、§2-5 配置校验语义对齐）。
  - 目的：`internal/watcher` 监听 configPath / auth-dir，rename 原子替换避免 watcher 读到半截 YAML/JSON。
- **验证点（现象/预期/方法/通过标准）**：
  - 现象：写 config / 写 auth 文件时若在中途 kill -9 进程，原 `os.WriteFile` 会留下半截文件。
  - 预期：磁盘上目标文件要么是完整旧值、要么是完整新值，**绝不出现半截**；临时 `.tmp` 不残留。
  - 方法：对三处分别在写盘后立即 `kill -9` / 强杀，重启宿主，观察 watcher 加载。
  - 通过标准：①重启后 watcher 解析 YAML/JSON 无 parse error；②目录下无 `*.tmp` 残留；③`config_yaml.go:102`、`auth_files_crud.go:272`、`config_load.go:223` 三处均已改走 `writeFileAtomic`，`grep -n "os.WriteFile" internal/config internal/api/handlers/management` 不再命中这三处业务写盘点。

### 补丁 2　`GET /readyz`（插件 dlopen 完成前 503；不查依赖；<1s 返回）

| # | 现状代码（实测锚点） |
|---|---|
| 现状 | `internal/api/server_routes.go:44-53` 已有 `healthzHandler`，注册 `s.engine.GET("/healthz", ...)` / `HEAD("/healthz", ...)`；**无 /readyz**。`internal/pluginhost/loader_windows.go:81` `syscall.LoadDLL` + `:86 FindProc("cliproxy_plugin_init")` + `:117` ABI 校验即插件 dlopen 全过程。 |

- **改动内容**：仿 `healthzHandler`（server_routes.go:44）新增 `readyzHandler`，注册 `s.engine.GET("/readyz", readyzHandler)`（+ 可加 HEAD）。数据源：pluginhost 暴露就绪态。
- **接口签名/行为**：
  - pluginhost 新增 `Ready() bool`（或等价：已成功加载且 enabled 的插件计数 > 0）。
  - 行为：
    - `Ready()==false`（pluginHost.ApplyConfig 未返回 / 尚无任一 enabled 插件 dlopen 成功）→ **HTTP 503**；
    - `Ready()==true` → **HTTP 200**。
  - **健康检查不查依赖**：`/healthz` 只判进程存活+监听（沿用现状）；`/readyz` **只判插件 host 就绪态，不向上游/插件内部发任何探测请求**，故 P99 < 1s。
  - 与探活配合（见《设计定稿1-4》§2.4）：TCP/healthz 通但 readyz 503 =「监听就绪、插件加载中」，面板先显示后端在线、渠道未就绪。
- **验证点（现象/预期/方法/通过标准）**：
  - 现象：起服早期插件 dll 尚未 dlopen 完成。
  - 预期：此窗口期 `GET /readyz` 返回 503；dlopen 完成后转 200；全程不触发任何上游/插件内部探测调用。
  - 方法：起服后立即高频轮询 `GET /readyz`（带 `X-Management-Key`，或按 healthz 同款不鉴权策略），观察状态翻转；同时在插件日志里确认 readyz 未引发额外 host call。
  - 通过标准：①dlopen 中观察到 ≥1 次 503、完成后稳定 200；②单次 /readyz 响应 < 1s；③`grep -n "readyz" internal/api/server_routes.go` 有 GET 注册；④pluginhost 有 `Ready()` 且 server_routes 引用它。

### 补丁 3　`POST /v8/management/shutdown`（复用 `service.Shutdown` 优雅停机）

| # | 现状代码（实测锚点） |
|---|---|
| 现状 | 已有优雅停机实现：`sdk/cliproxy/service_lifecycle.go:228` `func (s *Service) Shutdown(ctx context.Context) error`（内部 `shutdownOnce.Do` 幂等，可重复调用）；信号入口 `internal/cmd/run.go:45` `signal.NotifyContext(..., syscall.SIGINT, syscall.SIGTERM)`。**v8 管理组无 shutdown 端点**。v8 组注册见 `internal/api/server_management_v8.go:21-23`（`v8.GET/PUT/PATCH("/config", s.mgmt.ConfigV8)`）。 |

- **改动内容**：在 v8 management 组（`server_management_v8.go`，走 `mgmt.Middleware()` 鉴权）新增一条 `POST /shutdown`。
- **接口签名/行为**：
  - 路由：`v8.POST("/shutdown", s.mgmt.ShutdownHandler)`（新增 handler `ShutdownHandler`）。
  - 行为：handler 内**先回 200**，再异步 `go service.Shutdown(context.Background())` 停服——保证 DSH 收到「已受理」响应后进程才退出，避免连接被硬切。
  - 复用现有幂等停机路径（service_lifecycle.go:228，`shutdownOnce`），不另造停机序列。
  - 这是 DSH 停止序列首选（《设计定稿1-4》§3.2）：①POST shutdown → ②否则 Ctrl-C/SIGINT（run.go:45）→ ③兜底 taskkill → ④Job Object 父退子亡。
- **验证点（现象/预期/方法/通过标准）**：
  - 现象：DSH 需要主动停后端进程。
  - 预期：`POST /v8/management/shutdown`（带 management key）先回 200，随后进程优雅退出、端口释放、日志出现 shutdown 路径输出。
  - 方法：起服 → `curl -X POST .../v8/management/shutdown` 带 `Authorization: Bearer <secret-key>` → 观察 HTTP 状态与进程存活。
  - 通过标准：①响应 200 在进程退出前到达；②进程经 run.go:45 / service_lifecycle.go:228 路径优雅退出（非 SIGKILL）；③重复 POST 不 panic（shutdownOnce 幂等）；④未带 key 时 401/403。

### 补丁 4　key→unit 捷径（access 校验 key → 解析得 authID → 注入 `req.AuthID`）

> 核心：**复用宿主原生已有的 pinned 原语，宿主只加约 10 行映射注入**。原语链路已实测存在（见下），缺的只是「外部 key→authID 写入通道」。

| # | 现状代码（实测锚点） | 实测语义 |
|---|---|---|
| 原生已有 pinned 写入 | `sdk/api/handlers/model_execution.go:115`（`ExecuteModel`）与 `:151`（`ExecuteModelStream`） | `if req.AuthID != "" { ctx = WithPinnedAuthID(ctx, req.AuthID) }` —— **req.AuthID 非空即自动钉号** |
| pinned helper | `sdk/api/handlers/handlers_context.go:69` | `func WithPinnedAuthID(ctx, authID string) context.Context`（空白 authID 直接返回原 ctx） |
| pinned 常量 | `sdk/cliproxy/executor/types.go:36` | `PinnedAuthMetadataKey = "pinned_auth_id"` |
| metadata 写入 | `sdk/api/handlers/handlers.go:229-230` | `if pinnedAuthID := pinnedAuthIDFromContext(ctx); pinnedAuthID != "" { meta[coreexecutor.PinnedAuthMetadataKey] = pinnedAuthID }` |
| selector 钉号 | `sdk/cliproxy/auth/conductor_selection.go:1203` 与 `:1295` | `if pinnedAuthID != "" && auth.ID != pinnedAuthID { continue }` —— **命中后排除其它 auth，绝不 failover 到同 provider 别的号** |
| access key 现状 | `internal/access/config_access/provider.go:31`（struct）、`:33`（`keys map[string]struct{}`）、`:92`（`if _, ok := p.keys[candidate.value]; ok`） | **只是扁平 key 集合，只做「key 在不在」校验，Principal=key 串，无任何 model/provider/auth 绑定** |

- **改动内容（方案甲，约 10 行）**：
  1. DSH 经 Management API 维护一张映射 `map[apiKey]unit{provider, authID, model}`（首启注入，**映射全量幂等覆盖**：每次写=整体替换，不做增量 patch，避免残留脏映射）。
  2. 在 access 中间件**校验 key 通过之后**、进入转发之前：若该 key 命中 unit 映射，则 `ctx = WithPinnedAuthID(ctx, unit.authID)`（handlers_context.go:69 现成 helper）。
  3. 此后请求经 handlers.go:229-230 自动把 pinned_auth_id 写进 metadata → conductor_selection.go:1203/1295 selector 钉死该 auth。等价于「每单元一个 access key + key 绑定单元」。
- **组织者推荐默认（与 02/03 统一，三条）**：
  1. **写端点 = `PUT /v8/management/units`（幂等覆盖）**：DSH 经此端点整体写 `units[]` 映射，写即全量替换（不做增量 patch，避免残留脏映射）；与 §2-5「配置校验失败保留旧值」配合——校验失败则不写盘、返回 400、旧映射不动。
  2. **每单元 apiKey 注册走 access manager keys 注入**：注入位 = `internal/api/server_middleware.go:166-176`（`accessAuthMiddleware`；实测 `:166 result,err := manager.Authenticate(...)` 成功后 `:169-173 c.Set("userApiKey"/"accessProvider"/"accessMetadata", ...)` 再 `:175 c.Next()`）。单元 key 经 access manager 注入校验集，并在 `c.Next()` 前据 `result.Principal`（=apiKey）查 unit 映射 → `WithPinnedAuthID`。
  3. **单元失效状态码 = pinned 专属 503**：实测 `sdk/cliproxy/auth/conductor_home.go:994-996`——`pinnedAuthID != ""` 且 pinned auth 落在 `excludedAuthIDs`（本轮回被排除/禁用/冷却）时返回 `&Error{Code:"auth_not_found", Message:"pinned auth is unavailable in the current retry round", HTTPStatus: http.StatusServiceUnavailable}`（=**503**）。统一口径：pinned 钉死的号失效 → **503 + `auth_not_found` 文案**，与 02/03 一致（非 404）。
- **接口签名/行为**：
  - 新增 access 侧映射表结构 `unitMapping map[string]unitEntry`，`unitEntry{Provider string; AuthID string; Model string}`；新增查询 helper（如 `lookupUnitByKey(apiKey string) (unitEntry, bool)`）；写端点 `PUT /v8/management/units`（见上「组织者推荐默认」①）。
  - 命名三仓库统一：**单元字段 = `units[].apiKey` / `authRef` / `model`**；`authRef` 语义 = auths 文件 id/label。
  - **单元失效提示（pinned 专属 503 + 文案）**：pinned 到的 auth 被禁用/冷却/删除/本轮回被排除 → selector 无候选 → 转发返回 **503** + `auth_not_found` 文案（实测 conductor_home.go:996），**绝不自动落到同 provider 别的号**（这正是「绝不混用」要的行为）。
  - 映射写错 authID 时：pinned 无效 → selector 无候选 → 同上 503，不崩、不静默混用。
- **验证点（现象/预期/方法/通过标准）**：
  - 现象：DSH 给每单元一个独立 `/v1` 调用 key，要求该 key 只钉死本单元账号。
  - 预期：用单元 key 调 `/v1/chat/completions`，仅该 unit 的 auth 被用；同 provider 配两个 auth 时，日志只出现 pinned 那一个；该 auth 被禁用时返回 503+`auth_not_found` 文案，不 failover。
  - 方法：①配两 auth 同 provider，pinned 其一后发请求，抓日志；②把 pinned auth disable 再发请求；③用未登记映射的普通 key 发请求（应走正常 selector）；④`PUT /v8/management/units` 全量写一次映射。
  - 通过标准：①日志只出现 pinned auth ID，不出现另一个；②禁用 pinned auth → **503** 且文案含 `auth_not_found`/pinned-unavailable（conductor_home.go:996）；③普通 key 不被钉号、正常选号；④映射表由 `PUT /v8/management/units` 全量幂等覆盖写入。

## 2. 优雅化清单（一期 / 二期）

> 总原则：一期与瘦身重叠、零 ABI/端点风险、顺手做；二期低优先、纯内部整洁。**凡动插件 ABI/端点/契约必标「需插件集同步」，本阶段不做。**
> 基线核实（《13-后端优雅重构清单》）：logrus 260 文件 / ~880 调用点 / slog 零处；测试文件 761（906 用例）。

### 一期（顺手、零风险）
| # | 项 | 做法 | 验证 |
|---|---|---|---|
| 1 | **最小导出面** | 裁掉包的导出符号随包删；**保留包内「仅包内未被 sdk/api 引用」的 `Xxx` 导出改小写私有** | 编译即验（`go build ./...`） |
| 2 | v0 冗余 ~端点收敛 | 见补丁 5（留 catch-all） | 见补丁 5 验证点 |
| 3 | **命名统一** | 三仓库统一 `units[].apiKey` / `authRef` / `model`（host 侧映射表字段同名） | DSH↔宿主字段一致 |
| 4 | **错误码对齐 pluginabi Envelope** | 管理面统一 `{ok:false, error:{code,message,http_status}}`（对齐 pluginabi Envelope）；错误码：`auth_not_found`/`unknown_method`/`config_invalid`/`upstream_5xx`；转发面 `interfaces.ErrorMessage{StatusCode,Error}`，SSE 内 `data:` JSON | 信封形状与 Envelope 一致 |
| 5 | **配置校验失败保留旧值** | PATCH config 先校验新值，失败则**不写盘、不热重载**、返回 400 并保留旧配置（与补丁 1 原子写配合，避免半截配置挂掉后端） | 坏值 PATCH → 400 且 config.yaml 内容未变 |

### 二期（低优先、可晚做 / 可接受不做）
| # | 项 | 说明 | 标注 |
|---|---|---|---|
| 6 | internal/util + misc + constant 合并为 `internal/pkg` | 减少「到处都是 util」心智；合并动 import | 二期 |

## 3. SDK / ABI 版本对齐

> 判定：**这份插件 DLL 可原样加载到 v8 宿主，无需重编译、无需对齐 SDK。** 依据链 = C ABI 版本号相等(1) → LoadDLL+init 握手通过；结构体布局一致 → 内存安全；method 字符串一致 → 派发命中；payload 结构体一致 → JSON 编解码对齐；SchemaVersion 差由宿主向后兼容吸收。

### 3.1 版本常量（实测锚点）
| 侧 | 常量值 | 文件:行（实测） |
|---|---|---|
| 宿主 v8 `ABIVersion` | `uint32 = 1` | `sdk/pluginabi/types.go:7` |
| 宿主 v8 `SchemaVersion` | `uint32 = 6` | `sdk/pluginabi/types.go:20`（注释：v6=管理响应保留原始 JSON body、不做 HTML 转义） |
| 宿主运行时校验常量 | `pluginHostABIVersion = pluginabi.ABIVersion` (=1) | `internal/pluginhost/abi.go:9` |
| 宿主加载校验点 | `if client.api.abiVersion != pluginHostABIVersion { ... "plugin ABI version %d is not supported" }` | `internal/pluginhost/loader_windows.go:117-119` |
| 插件 SDK v7.2.30 | `ABIVersion = 1`、`SchemaVersion = 1`（v7 types.go:7 / :11） | 插件 go.mod 钉 `.../v7 v7.2.30` |

- **`ABIVersion` 两边都 = 1 → 校验通过，DLL 可加载。**
- **唯一版本差**：`SchemaVersion` v7=1 vs 宿主 v8=6。这是注册时协商的 RPC 行为版本，宿主对旧 schema 向后兼容（自动退回旧逐 chunk 行为），**非加载阻塞项**。本插件未注册 stream 拦截器，该差异实际无影响。

### 3.2 升级成对规则
| 宿主 SDK | 插件 SDK | ABIVersion | SchemaVersion | 结论 |
|---|---|---|---|---|
| v8.0.7 | v7.2.30（本 bridge/workbuddy） | 1=1 ✅ | 1 vs 6 协商兼容 | **可加载**；插件按旧 schema 行为，宿主自动适配 |
| v8.0.7 | v8.x（重钉后） | 1=1 ✅ | 6=6 | 可加载 + 享新 RPC 行为（管理响应不 HTML 转义、流式 chunk 精简） |
| 宿主未来 v9 | v7.2.30 | 若 v9 抬走 ABIVersion | — | **可能加载失败** → 必须成对升级 |
| 宿主 v8.0.7 | 更早插件（ABIVersion≠1） | 不等 | — | loader 报 abi_version 不支持（loader_windows.go:117） |

- **成对升级规则**：宿主升 SDK → 插件 go.mod 重钉到同版 → 双产物（exe + dll）**同发同验**。DSH 首启「拉 dll + 校验 SHA-256」为必加步骤（不能假设用户自备 dll）。

### 3.3 Windows 构建链（插件 dll 必须 cgo；宿主 exe 零 cgo）
- **宿主 exe = 零 cgo**：`internal/pluginhost/loader_windows.go`（`//go:build windows`）纯 syscall 加载——`:81 syscall.LoadDLL(loadPath)`、`:86 dll.FindProc("cliproxy_plugin_init")`、全程**无 `import "C"`**（实测确认）。故编译宿主 exe 不需要 mingw。
- **插件 dll 必须 cgo + c-shared**：要导出 C 符号供宿主 GetProcAddress。命令（与 `cpa-multi-plugins/scripts/build.sh` 同款，实测 :38/:47/:59）：
  ```bash
  export GOOS=windows GOARCH=amd64 CGO_ENABLED=1
  export CC=x86_64-w64-mingw32-gcc   # MSYS2 MINGW64 下也可直接 CC=gcc（等价）
  go build -buildmode=c-shared -trimpath -ldflags="-s -w" -o <plugin>.dll .
  ```
  工具链：Go ≥ 1.26 + MSYS2 MINGW64（`mingw-w64-x86_64-gcc`）。
- **分发结论**：插件 dll 必须从 Release 预编译分发，不让 DSH 用户本地 go build；DSH 首启=拉 zip → 校验平台/文件名/SHA-256 → 解压落 `plugins/` → 写 config 启用。
