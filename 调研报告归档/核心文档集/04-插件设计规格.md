# 04 · 设计规格（插件侧）—— dsh-cpa-panel 实施详规

- 日期：2026-10-03 ｜ 性质：整理轮产物，只读设计文档，**不改任何代码**
- 地位：本卷为「实施 agent 的插件侧规格」，全量吸收《产物2-C：dsh-cpa-panel 插件改造详案》，并并入 UI/UX 专项、UI 多版本方案、UI 定稿（含修正）、UI 层级与复用清单、现有 UI 解剖、DSH 官方风格贴合、bridge 工程拆解、简单配置页契约、TS 迁移评估。冲突处效力见 §0。

- 已锁方向（不可推翻）：主功能=养号自动化；独立调用单元 `units[]`；养号开关 autoCheckin 默认 true / autoTasks 默认 false / normalizeSchedulerMode 默认 true；思考强度全局默认 medium、每单元可覆盖；CPA 内置 UI 全删、唯一 UI=插件页；宿主半端照 bridge 模板 TS 化、client.js 保留 JS 改造（路径 B）、schemastery 配置表单（路径 C）；进程托管 Job Object 父退子亡 + 退避重启 + 非 shell spawn；首启自动写最小 config.yaml（随机 secret-key）+ 拉取/校验 exe 与 dll（SHA-256）。

## 1) 插件工程骨架

### 1.1 目标目录树

照 bridge 模板，但**只取骨架、不取依赖**（见 §1.3）。client.js 保留 JS 不 TS 化（路径 B）。

```
dsh-cpa-panel/
├── package.json                 # 重写（见 §1.3，补 cordis peer + primitives/atomic-write deps + 修 dsh.client.inject）
├── tsconfig.json                # 宿主半端 TS 配置（ESM，NodeNext；include src+tests，exclude src/client）
├── tsconfig.client.json          # 浏览器半端配置（jsx react-jsx + lib dom；仅语法检查 client.js，不产出 bundle）
├── tsdown.config.ts             # 双配置：宿主 ESM lib/index.js + lib/*.d.ts；浏览器侧不打包（client.js 原样发布）
├── vitest.config.ts             # 单测：units 校验 / config 生成器 / adapters 纯函数
├── cordis.patch.yml             # 照旧：insert 一行 id/name=dsh-cpa-panel
├── icon.svg                     # 照旧
├── src/
│   ├── index.ts                 # 宿主入口（原 index.js→TS）：name/inject/Config/apply/路由注册
│   ├── adapters.ts              # 四渠道差异层（原 adapters.js→TS）
│   ├── units.ts                 # 【新】Unit 类型 + units[] 校验 + key→unit 映射
│   ├── process.ts               # 【新】进程托管：Job Object/非 shell spawn/退避重启/父退子亡
│   ├── bootstrap.ts             # 【新】首启：定位 exe/dll、SHA-256 校验、生成最小 config.yaml
│   ├── client/
```

### 1.4 cordis.patch.yml 两常量（ENTRY_ID vs BUNDLE_NAME 分钉）

照 bridge 红线——两个常量分开钉死，防日后改名踩坑：

| 常量 | 取值 | 对齐点 |
|---|---|---|
| `ENTRY_ID` | = patch insert 的 `id` = `configForms.get()` 的**设置命名空间** | 现状 = `dsh-cpa-panel`（patch.yml 实测） |
| `BUNDLE_NAME` | = `pkg.name` = `slots.register({key})` | 现状 = `dsh-cpa-panel`（package.json 实测） |

本仓当前两者恰好都是 `dsh-cpa-panel`（patch.yml 实测 `id/name` 同为该值），**仍按 bridge 方式显式分两常量**，不合并。⚠待核对：`index.js:36` 的 `name='cpa-panel'` 与上述不一致——实施时需确认 loader 诊断名是否要一并改为 `dsh-cpa-panel`，避免 whileServed/命名空间错位。

### 1.5 其他工程约束

- **lockfile 坑**：插件必须落在 profile `node_modules/` 真实目录、不用 `link:` 外指（README 实测坑）；所有临时装包/核验目录放**仓库外**，CI 用 `--frozen-lockfile`，发现脏记录 `pnpm install` 重解析、不手编 lockfile（bridge §3.2）。
- **TS 产物形态**：`tsdown` 产 `lib/index.js`(ESM) + `lib/index.d.ts`；client.js 原样发布不打包、不进编译。
- **DSH 宿主零改动**：`cordis.patch.yml` 机制照旧，不要求宿主侧任何补丁。

### 1.6 命名与品牌（Panel 改名 · 待拍板 00 §5⑩）

现状：插件已从「面板」进化为**完整独立功能**（托管进程 / 单元管理 / 养号自动化 / 模型直选），`cpa-panel` 名不副实。三层改名方案：

| 层 | 位置（实测锚点） | 现值 | 改法 | 兼容风险 |
|---|---|---|---|---|
| **L1 显示名/发布名** | package.json `name`（npm/插件商店发布名）；README 标题；index.js:36 `name='cpa-panel'`（loader 显示名） | `dsh-cpa-panel` / `cpa-panel` | **直接改为新名** | 零；发布名变更，发布时确认 npm 同名包占用 |
| **L2 设置命名空间** | index.js:33 `ENTRY_ID='dsh-cpa-panel'`（= patch insert `id` = configForms 命名空间，见 §1.4） | `dsh-cpa-panel` | **方案 B1（推荐）：保留现值**——用户已存配置全挂在旧命名空间，改名即丢配置；ENTRY_ID 是内部稳定标识、用户不可见 | B1 零；B2（改新名+读旧命名空间迁移）需迁移代码+版本升级路径，不推荐首版 |
| **L3 附属标识** | storage `cpa-panel-checkin.json`（index.js:98 实测）；logger 前缀 `cpa-panel:`；CSS 类前缀 `cpa-` | 见左 | storage/logger 随新名改（签到去重记录可迁移或接受重签一次）；CSS 类 `cpa-` **保留**（品牌一致） | storage 改名=签到去重记录丢失（低，可接受） |

新名字候选（推荐排序，包名用 `dsh-` 前缀、显示名中文可并列）：

- **A（推荐）`dsh-cpa-hub`**，显示名「CPA Hub · 多渠道中转站」——管理枢纽语义（渠道×账号×模型），保留 cpa 品牌识别度，克制不夸大
- B `dsh-cpa-autopilot`，显示名「CPA 养号助手」——强调签到/任务/保活自动化
- C `dsh-cpa-operator`，显示名「CPA 操作台」——强调运维操作语义

**推荐组合**：L1 改 **A** + L2 走 **B1**（ENTRY_ID 保留 `dsh-cpa-panel`）+ L3 随新名（storage 迁移或重签一次）。
**实施注意**：ENTRY_ID 与 BUNDLE_NAME 继续分钉两常量（§1.4 红线），改名只动可见层（L1）与附属标识（L3），不动命名空间（L2）。

## 2) schemastery schema 全字段

> 全部字段 `.volatile()`（现状 8 字段已全 volatile，实测 `index.js:57-72`）。硬规则：`.default()` 必须在 `.volatile()` 之前；取值在使用点 `refs.x.get() ?? 默认`，绝不把值 capture 进闭包；全 volatile 才进宿主表单、改值不重挂插件。units[].apiKey 与产物2-A 的 key→unit 映射同名字段对齐。

### 2.1 连接与生命周期（6 项）

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `adminKey` | `z.string().role('secret')` | `''` | CPA management 密钥（留空走凭据引用）；实测 `index.js:58` |
| `adminKeyRef` | `z.string().role('credential-ref')` | `'CPA_ADMIN_KEY'` | 凭据库引用名；实测 `index.js:59` |
| `port` | `z.natural().min(1).max(65535)` | `8317` | CPA 监听端口；baseURL `http://127.0.0.1:<port>`（host 恒 loopback） |
| `exePath` | `z.string()` | `''` | 空=自动定位+校验；非空则按此 spawn |
| `manageLifecycle` | `z.boolean()` | `true` | 进程托管开关（false=退化为纯 UI，不自启 CPA） |
| `startTimeoutSeconds` | `z.natural().min(3).max(180)` | `30` | 探活超时（waitForPort 上限） |

~~`openControlPanel`~~：**删**（CPA 内置 UI 全弃）。旧字段 `autoCheckinOnStart` 按 §2.3 改名合并。

### 2.2 units[]（独立调用单元）

```ts
units: z.array(z.object({
  channel: z.union([z.const('workbuddy'), z.const('trae'),
                    z.const('qoder'),   z.const('zcode')]),
  authRef: z.string(),                 // auth 文件 id/label（与 /accounts[].auth_id、/auth-files[].name 逐字 join）
  model:   z.string(),                 // 空 = 跟随渠道默认
  enabled:  z.boolean().default(true),  // = auth-files/status.disabled 的反向
  apiKey:   z.string().role('secret'),// 每单元独立 API key（与产物2-A key→unit 映射同名字段）
  reasoningEffortDefault: z.union([z.const('auto'), z.const('off'), z.const('low'),
                                   z.const('medium'), z.const('high')]).default('auto'),
})).default([]).volatile(),
```

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `units[].channel` | 四渠道联合 | — | workbuddy/trae/qoder/zcode（由已加载 .dll 决定） |
| `units[].authRef` | string | — | 账号引用 = auth 文件 id/label（与 `/accounts[].auth_id` join） |
| `units[].model` | string | `''` | 空=跟随渠道默认；非空=锁定模型 |
| `units[].enabled` | boolean | `true` | 单元总开关（底层写 `auth-files/status{disabled}`） |
| `units[].apiKey` | `role('secret')` | `''` | **每单元独立 API key**；DSH→CPA 的 Bearer 来自此 |
| `units[].reasoningEffortDefault` | 五档联合 | `'auto'` | 覆盖全局默认 |

### 2.3 养号三开关 + 全局思考强度

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `autoCheckin` | `z.boolean()` | **`true`** | 自动签到（含首启补签） |
| `autoTasks` | `z.boolean()` | **`false`** | 定时跑成长任务（行为重、误触/封号风险高，用户显式开） |
| `normalizeSchedulerMode` | `z.boolean()` | **`true`** | 启动时归一 `scheduler_mode=off`（单元锁定前提=调度器可控） |
| `reasoningEffort`（全局） | 五档联合 | **`'medium'`** | 全局思考强度默认，单元可覆盖 |

**改名与兼容**：旧字段 `autoCheckinOnStart`（`index.js:63`，默认 true，开机补签）→ 并入新字段 `autoCheckin`（默认 true，语义=自动签到含首启补签）。迁移期宿主 remount 时做一次旧值→新值映射：若配置里仍存 `autoCheckinOnStart`，读路径回退 `refs.autoCheckin.get() ?? refs.autoCheckinOnStart.get() ?? true`，避免老用户升级后开关突变。

> 全局 `reasoningEffort` 默认值：旧《UI定稿修正》曾写 `'auto'`，本卷按任务要求与主线收敛为 **`'medium'`**。透传落点见 §6 V5（CPA 当前 16 条调用无对应写端点，标待验证）。

### 2.4 首启生成的 config.yaml 字段（宿主真实 yaml tag，已勘误）

## 3) 插件 ↔ CPA 通信契约

### 3.1 端点清单

| 端点 | 方法 | 用途 | 分支 |
|---|---|---|---|
| `/healthz` | GET/HEAD | 存活/监听就绪 | 共用（已有） |

### 3.2 鉴权握手

1. 首启：插件生成 `remote-management.secret-key`（32B base64url）→ 原子写 config.yaml（同写顶层 `host/port/auth-dir/api-keys`，字段路径一律以《09-直抄稿》§3 勘误表为准）→ 拉起 CPA。
2. 之后所有 management 请求带头 `Authorization: Bearer <secret-key>`（或 `X-Management-Key`）；`resolveAdminKey` 优先级：配置 `adminKey` 显式值 → 凭据库 `adminKeyRef`（`CPA_ADMIN_KEY`）→ 空（空密钥时写操作一律 `no-admin-key`，不静默失败）。
3. 验证：`GET /v0/management/config` 返回 200 即握手成功。
4. loopback 隔离：CPA 绑 `127.0.0.1` 天然隔离；DSH 侧额外校验响应来源为 loopback，`Host` 头=`127.0.0.1:<port>`、`remote-management.allow-remote=false`。

### 3.3 错误码与超时

| 情形 | CPA 行为 | DSH 处理 |
|---|---|---|
| 未配 secret-key | Management API 整体 404 | 视为「未初始化」，走首启 |
| 错 key | 401/403 + 5 次失败 30 分钟 IP 封禁 | 不重试，提示密钥错；不静默 |
| 成功 | 2xx + `{ok,result}` 信封 | 正常 |
| 超时默认 | — | management 请求 5s；拉余额 10s；流式转发 DSH 不介入（只控制面） |

### 3.4 探活三级退避

1. **TCP 探活**：起服务后先探 `127.0.0.1:port` TCP 连通（`probePort`，实测 `index.js:132`）。
2. **监听就绪**：TCP 通 + `GET /healthz` 200。
3. **插件就绪**：`GET /readyz` 200（插件 host init 完成前返 503）。

间隔/退避：0ms→100ms→300ms→1s→2s，上限 5s 一轮；总等待由 `startTimeoutSeconds`（默认 30s）兜底。区分：TCP/healthz 通但 readyz 503 =「监听就绪、插件加载中」，面板可先显示后端在线但渠道未就绪。

## 4) 首启状态机

### 4.1 七步流程（每步含失败处理）

| 步 | 动作 | 失败分支 |
|---|---|---|
| 1 定位 exe | `exePath` 配置 → `defaultExeCandidates()`（实测 `index.js:84`）探测常见位置 → 都没有则从 Release 下载 | **F1 下载失败**：报「未找到/无法下载 cli-proxy-api.exe」，重试 3 次仍失败终止 |
| 2 校验 exe | 文件名/平台（windows-amd64）/SHA-256 对清单 | **F2 校验失败**：删除重下；仍失败报「exe 校验失败」，不静默用旧文件 |
| 3 拉 dll | 从 Release zip 拉 `plugins/*.dll`，校验 SHA-256 | 校验不过删除重拉；仍失败报「插件完整性校验失败」，不启动带损坏插件的后端 |
| 4 生成 config.yaml | **原子写**：`config.yaml.tmp` → fsync → rename（防 watcher 读半截）；写前备份原 config.yaml（`.bak`） | 写失败回滚删 tmp 重试；仍失败报「配置写入失败」 |
| 5 拉起 | **非 shell spawn**，固定参数数组 `[exe, '--config', configPath]`（+ `-no-browser`），`windowsHide`、代理变量清空、挂 **Job Object** | **F3 端口占用**/启动失败：退避重启（指数+抖动，上限 5 次/5 分钟窗），不打死循环 |
| 6 探活 | TCP→/healthz→/readyz（§3.4 策略） | **F5 秒崩**：进程秒退读 `crashExitCode`，超 startTimeout 未就绪→读日志最后行回显错误 |
| 7 回显 | 握手 `GET /v0/management/config` → 渲染单元/状态页；`remote-management.secret-key` **双写回显**（见下注 G3） | 握手失败报「后端已起但管理接口不可用」 |

> **secret-key 回显（11 审计 G3，组织者推荐）**：首启生成 `remote-management.secret-key` 后**双写**——① 写 DSH 凭据库（`ctx.credentials`，键名 `CPA_ADMIN_KEY`，即 `adminKeyRef` 默认值）；② 面板 status 回显。这样 `adminKeyRef` 直接从凭据库解析，用户无需手填 adminKey，开箱即用。

### 4.2 「已在跑就复用」（attach 分支 F4）

起服务前先 TCP + `/healthz` 探活：通则**不重复拉起**，直接复用（记录其端口，标 `owned=false`）。无锁文件，探活是唯一判据。

### 4.3 五失败分支归纳

| 代号 | 分支 | 面板表现 |
|---|---|---|
| F1 | 下载失败（exe/dll 拉不到） | 状态条 StateDot=error + 文案「未找到/无法下载」 |
| F2 | SHA-256 校验失败 | 状态条「exe/dll 校验失败」；不静默用旧文件 |
| F3 | 端口占用 / 启动失败 | 退避重启 N 次后 error；状态条挂原因 |
| F4 | 已在跑（healthz 通） | 复用 attach，`owned=false`，不重复 spawn |
| F5 | 秒崩（crashExitCode） | StateDot=error + 退出码；读日志末行回显 |

### 4.4 停止序列与父退子亡

1. 首选 `POST /v8/management/shutdown`；
2. 否则向进程发 Ctrl-C/SIGINT（CPA 已优雅停机）；
3. 兜底：超时 5s `taskkill /PID`，再 3s 仍存活 `taskkill /F`；
4. **Job Object 父退子亡**：DSH 插件退出时 Job Object 确保 CPA 子进程一并回收，杜绝孤儿（不残留 cli-proxy-api.exe）。

**结论：机制成立，= `inject:['llm']` + `ctx.llm.registerAdapter()`**，不是 client 注入选择器、也不是 bundle patch。逐环证据（bridge 源码实测）：

**对 cpa-panel 的复制方法**：CPA 本身就是 OpenAI 兼容端点（`127.0.0.1:8317/v1`）。照 bridge 注册**每个渠道一个 pi-ai provider**（provider id = channel）：`baseUrl = http://127.0.0.1:8317/v1`，`resolveApiKey = units[].apiKey`（DSH→CPA 的代理 key），模型条目 = 该渠道下各单元的模型。用户在 DSH 对话窗原生 ModelSelect 直接看到「渠道分组 → 单元模型」，零手填地址/模型名。

**模型 id 编码**：
- provider id = 渠道（`workbuddy`/`trae`/`qoder`/`zcode`），一组一 provider；
- model id = **`<上游模型名>@<authRef>`**，如 `claude-sonnet-4@workbuddy-cherry`；选它 = 选「WB 渠道·cherry 账号·sonnet」这个单元；
- picker 显示名 = **`<账号昵称> · <模型名>`**，如 `cherry · claude-sonnet-4`；
- picker 提交 `{provider: channel, model: "<model>@<authRef>"}` → 宿主按 `(channel, authRef)` 反查 `units[]` → 取该单元 `apiKey` 作为 Bearer 发往 CPA `/v1`。

> ⚠待验证（V3）：bridge 的 shim 在**插件进程内**按请求注入真实上游凭据；而 cpa-panel 的真实账号凭据在 **CPA 进程**里、CPA 默认按自己的 routing 策略选号。「单元=锁定单账号」能否由 CPA 按 model id 精确路由，取决于 CPA 是否支持 per-request 钉 auth——见 §6 V3。

- **通过标准**：registerAdapter/emit 不报错、不抛类型错。

### V3 · 单元锁号——CPA 能否按 model id 钉 auth（或禁用其余 auth 兜底）
- **现象**：发 `model=<m>@<authRef>` 到 CPA `/v1/chat/completions`，请求落在哪个号、是否混用。
- **预期**：支持按 model id 精确钉到某 auth，或可绕过。
- **验证方法**：向 CPA `/v1/chat/completions` 发 `model="<m>@<authRef>"`，观察落在指定 auth 还是被 routing 策略切走。
- **通过标准**：请求落在指定 auth、不混用；**若 CPA 不支持 per-request 钉 auth，则兜底**——用 `units[].enabled=false` 禁用其余 auth（只留目标单元参与调度）+ `scheduler_mode=off` 保证精确路由，验证锁定成立。

### V4 · 单元级 apiKey（units[].apiKey）与 CPA api-keys 的对应
- **现象**：每单元独立 key 是否可鉴权、互不通用。
- **预期**：每单元独立 key 可鉴权。
- **验证方法**：用不同单元 key 发请求。
- **通过标准**：各 key 独立鉴权、互不通用；错 key 401。

### V5 · reasoningEffort 透传
- **现象**：picker 选 effort → CPA 请求是否带对参数到上游。
- **预期**：effort 正确透传。
- **验证方法**：发请求抓 wire。
- **通过标准**：`reasoning_effort` 正确到达上游；**落点待定**（CPA 当前 16 条调用无对应写端点）：候选是 CPA 全局 `/v0/management/config` 的请求级设置，或单元调用时的请求注入。

### V6 · provider 注册后 listProviders 是否立刻带模型（无空窗）
- **现象**：注册 provider 后 `listProviders` 是否立刻带模型，历史会话恢复是否首条失败。
- **预期**：无 UNKNOWN_MODEL 空窗。
- **验证方法**：照 bridge「先采纳身份再注册」三相顺序（先读凭据采纳身份 → 再注册 provider → 最后抓目录）。
- **通过标准**：注册即带模型，历史会话恢复不首条失败。

## 7) 验收（合并产物2-C §7）

1. **TS 编译与 dts**：`tsc --noEmit` 零错；`tsdown` 产 `lib/index.js`(ESM)+`lib/index.d.ts`；client.js 不参与编译，原样落在 `lib/client/client.js`。
2. **schema 表单自动渲染**：`Config` 全 volatile，宿主设置页自动出全部字段（含 units[] 数组行），改值不重挂插件，`refs.x.get()` 现读。
3. **首启状态机**：定位 exe→SHA-256 校验→写最小 config.yaml（随机 secret-key）→spawn 拉起→healthz/readyz 探活→状态条回显「运行中」，任一步失败挂对应原因。
4. **Job Object 父退子亡**：DSH 退出后 CPA 子进程被回收（不残留 cli-proxy-api.exe），非 shell spawn、`windowsHide`、代理变量清空。
5. **dll SHA-256 失败路径**：校验不过则不拉起，状态条报「dll 校验失败」，不静默用旧文件。
6. **探活退避**：拉起后按 0ms→100ms→300ms→1s→2s 轮询直到 startTimeout；启动失败退避重启不打死循环。
7. **单元列表 join**：`GET /api/v1/cpa/units` 返回 units[] 配置与 live accounts/credits 按 `(channel,authRef)` join，余额/签到徽标正确落行。
8. **批量签到 Modal**：点「全部签到」先弹 Modal 确认「N 个账号」，确认后逐账号 POST checkin，行级 busy 锁，失败行内错误条不擦屏。
