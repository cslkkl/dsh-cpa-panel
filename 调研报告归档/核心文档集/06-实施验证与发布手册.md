### 1.1 升级成对规则（SDK 版本兼容表，发布页必附）

| 宿主 exe SDK | 插件 dll SDK | ABIVersion | SchemaVersion | 能否直接加载 |
|---|---|---|---|---|
| **v8（本项目）** | **v7.2.30（现钉）** | 1 = 1 | 宿主 6 vs 插件 1（注册时协商，宿主向后兼容） | ✅ 可直接加载（已核验） |
| v8 升级 minor（ABIVersion 仍=1） | v7.2.30 | 1 = 1 | 6 vs 1 | ✅（dll 可滞后） |
| 宿主升 ABIVersion=2 | 必须用 v2 SDK 重编 | 1 ≠ 2 | — | ❌ 加载被拒（`loader_windows.go:117` 校验挡） |

**规则**：
- **ABIVersion 是硬门禁**（不等即拒载）——常量 `pluginabi.ABIVersion=1`（宿主 `sdk/pluginabi/types.go:7`）；插件编译时 import 的 SDK v7.2.30 决定它自报的 ABIVersion/SchemaVersion。
- **SchemaVersion 走协商向后兼容**（宿主容忍旧值）——宿主 v8=6，插件 v7.2.30=1，宿主按「旧 schema」路径多传 `OriginalRequest/HistoryChunks`，插件未注册 stream 拦截器故无感。
- **成对升级触发**：宿主升 ABIVersion 大版本时，所有渠道 dll 必须用新 SDK 重编并同发；正常 minor 升级（SchemaVersion 协商兼容）时 dll 可滞后。
- 插件每插件独立 go.mod，钉 `github.com/router-for-me/CLIProxyAPI/v7 v7.2.30`（5 个 go.mod 已核验同版）。

## 2. 构建链手册（Windows 产物从哪来）

> 根本约束（已核验）：**插件 dll 必须 cgo**（-buildmode=c-shared 导出 C 符号 `cliproxy_plugin_init`，把整套 Go runtime 打进 dll）；**宿主 exe Windows 端可零 cgo**（`internal/pluginhost/loader_windows.go` 纯 syscall：`syscall.LoadDLL`/`NewCallback`/`SyscallN`，整个 Windows exe 不 import C）。

### 2.1 宿主 exe（cli-proxy-api.exe）

- **目标主路径（纯 Go，瘦身后）**：
  ```
  CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o cli-proxy-api.exe ./cmd/server
  ```
  依据：loader_windows.go 纯 syscall 加载 dll，无需 MinGW。**需 V5 冒烟确认 CGO=0 仍能加载 workbuddy.dll**。
- **已验证路径（proven，CGO=1）**：仓库自带 `build-local.ps1`——`$env:CGO_ENABLED="1"`（:23）+ 仓库 `.toolchain/mingw64/bin/gcc.exe`（:17-22 注入 PATH）+ `go build -ldflags="-s -w -X main.Version=... -X main.Commit=... -X main.BuildDate=..." -o $out ./cmd/server`（:39）。Go 1.26。
- **MinGW 组件**：CGO=1 路径需 `mingw-w64-x86_64-gcc`；CGO=0 路径不需要。仓库 `.toolchain/mingw64/gcc.exe` 未随当前检出落盘，构建机自备或走 CI。
- **建议**：先 CGO=1（build-local.ps1）出可用包，V5 确认后切 CGO=0 瘦身。

### 2.2 渠道 dll（c-shared，4 个）

```bash
# MSYS2 MINGW64 shell 内（每插件独立目录，独立 go.mod，钉 SDK v7.2.30）
export GOOS=windows GOARCH=amd64 CGO_ENABLED=1
export CC=x86_64-w64-mingw32-gcc     # MSYS2 MINGW64 也可直接 CC=gcc（已把交叉 gcc 暴露成 gcc）
cd plugins/<id>
go mod download
go build -buildmode=c-shared -trimpath -ldflags="-s -w" -o <id>.dll .
```

- 产物名 = `<plugin>.dll`（workbuddy/qoder/trae/zcode 各一）。
- 构建机要求：Go ≥ 1.26 + MSYS2 `msystem: MINGW64` + 包 `mingw-w64-x86_64-gcc`。
- 发布前必改：`release.yml` PLUGINS 去 mimo（见 §2.3）、`scripts/build.sh` 插件清单补 zcode。

### 2.3 与 cpa-multi-plugins 现有 build.sh / release.yml 的异同（已对照源码）

| 维度 | `scripts/build.sh`（本地脚本） | `.github/workflows/release.yml`（CI） | 本轮要改什么 |

## 3. Release 发布流程（GitHub，用户执行）

### 3.1 版本语义与成对升级
- 宿主 exe：`v1.0.0` 起语义化（breaking 升 minor，补丁升 patch）。
- 插件 zip：独立 tag 或随宿主 tag 带后缀（如 `v1.0.0-plugins`）。
- DSH 插件：package.json version，tag `vX.Y.Z`。
- **成对升级**：见 §1.1 兼容表。发布页必附该表。

### 3.2 Release 内容模板
```
Release v1.0.0
├─ cli-proxy-api.exe                       (Windows amd64)
├─ cpa-multi-plugins-windows-amd64.zip     (4 dll: workbuddy/qoder/trae/zcode)
├─ dsh-cpa-panel-v1.0.0.tgz
└─ SHA256SUMS.txt
附：CHANGELOG.md（删了什么[R13 内置族]/加了什么[单元/养号/UI]/breaking 提示）+ SDK 兼容表（§1.1）
```

### 3.3 SHA-256 清单格式与校验
```
<64位hex>  cli-proxy-api.exe
<64位hex>  cpa-multi-plugins-windows-amd64.zip
<64位hex>  dsh-cpa-panel-v1.0.0.tgz
```
- 生成：Linux `sha256sum * > SHA256SUMS.txt`；Windows `Get-FileHash -Algorithm SHA256`。
- **DSH 插件首启按此清单校验**（bootstrap.ts verifyDll）：文件平台校验 → SHA-256 比对 → 通过才解压落地；失败不拉起、不静默用旧文件（V16）。

### 3.4 分发路径
- **A. 本地投放（首版推荐）**：插件包放 DSH profile `node_modules/`；exe/dll 由插件首启从 Release URL 拉取 + SHA-256 校验。
- **B. 插件商店**：cpa-multi-plugins 的 `registry.json` 当前**无 `install.artifacts`**（已核验），需补 artifacts 字段（URL+SHA256+platform）才能在线安装；公开分发时再补。
