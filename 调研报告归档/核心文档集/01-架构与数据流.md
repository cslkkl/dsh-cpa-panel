## 0. TL;DR（压缩结论）

整个系统是一条**六层管道**：

```
浏览器 React UI（client.js）→ DSH Node 宿主半端（index.js，持 adminKey、spawn CPA）
  → CPA Go exe（Gin，127.0.0.1:8317：/v1 转发面 + /v0|/v8 管理面）
  → C ABI v1（LoadLibrary/dlopen + cliproxy_plugin_init 交换两张函数表）
  → 插件 .dll（method 字符串 RPC 分派）→ 上游 HTTPS（OpenAI 形状 SSE）
```

- **密钥只在 DSH Node 宿主半端**：浏览器半端永远拿不到 adminKey（`client.js:11` 铁律，实测），只经同源 `/api/v1/cpa/*` 取数据。
- **CPA 是单进程 Gin**：`/v1/*` 转发面（Bearer `access.api-keys`）与 `/v0|/v8/management/*` 管理面（Bearer `secret-key`=adminKey）是**两套独立密钥**。
- **插件 = 进程内 C ABI 动态库**：宿主 `syscall.LoadDLL`（Win）/ `dlopen`（Unix）→ `dlsym("cliproxy_plugin_init")` 交换 `cliproxy_host_api`/`cliproxy_plugin_api` 两张函数表 → 之后 method 字符串 JSON-RPC。
- **ABIVersion=1 / SchemaVersion=6**：C ABI 形状 v1 不变；插件注册时协商 RPC JSON schema 版本（宿主 v8=6，插件集钉 SDK v7.2.30）。

## 2. 三条主数据流

### 2.1 调用链（按单元转发 chat）

```
中转客户端/DSH chat
  │  POST /v1/chat/completions（Bearer access.api-keys 里的单元 key）
  ▼
[L2] server_routes.go:67  v1.POST("/chat/completions")
  │  :64 AuthMiddleware(accessManager) 校验 key
  ▼
[L2] sdk/api/handlers/openai/openai_handlers.go:115  ChatCompletions（实测行号见源文档，⚠以仓库当前行为准）
  │  → ExecuteStreamWithAuthManager → applyModelRouter 模型路由
  │  钉号：model_execution.go:114-115 / :150-151
  │         if req.AuthID != "" { ctx = WithPinnedAuthID(ctx, req.AuthID) }
  │         pinned_auth_id 键 = executor/types.go:36（实测）
  ▼
[L2] pluginhost 按 plugin.register 声明，命中插件 executor
  │  C ABI：cliproxyPluginCall("executor.execute_stream", payload)
  ▼
[L3] workbuddy/main.go:266  case MethodExecutorExecuteStream → handleExecStream
  ▼
[L4] host.http.do 或自带 httpclient → copilot.tencent.com/v2/chat/completions（main.go:103）
  ▼

  ▼
```

**经过的文件/端点**：`/v1/chat/completions`（`server_routes.go:67`）→ `AuthMiddleware`（`:64`）→ `openai_handlers.ChatCompletions` → `handlers_stream.go` 执行骨架 → `WithPinnedAuthID`（`handlers_context.go:69`；注入点 `model_execution.go:115/151`）→ `pluginhost` → C ABI `executor.execute_stream`（`workbuddy/main.go:266`）→ 上游 `POST /v2/chat/completions`（`workbuddy/main.go:103`）→ SSE 经 `host.stream.emit` 回流。

**经过的文件/端点**：`client.js` → `/api/v1/cpa/{action,auto-checkin,scheduler-mode}`（`index.js:940/972/919`）→ `cpaFetch`（`index.js:168`）→ `/v0/management/plugins/<provider>/*` → catch-all `pluginManagementNoRoute`（`server_management.go:254`）→ `ServeManagementHTTP`（`:285`）→ `management.handle`（`workbuddy/main.go:282`）→ 上游。自动调度旁路：`workbuddy/checkin.go:29` `go schedulerLoop`。

## 3. 模块边界与依赖方向（防屎山规则）

### 3.1 宿主（Go / CLIProxyAPI）internal 分层

```
cmd/server/main.go（入口；:38 匿名 import translator 是唯一硬耦合点 ⚠实测行号以仓库为准）
   └─► internal/api（装配/路由）
         ├─ server_routes.go     /v1 转发面 + /healthz
         ├─ server_management_v8.go  /v8/management
         ├─ server_management.go      /v0/management + catch-all
         └─ handlers/management/  账号 CRUD/启停/刷新/quota/config
               └─► internal/config（v8 读写、原子写）
               └─► internal/pluginhost（LoadDLL 加载 + method 派发 + quota）
               └─► internal/watcher（config+auths fsnotify 热重载）
               └─► internal/access（api-keys 鉴权）
               └─► sdk/cliproxy/auth（Manager/Selector 选号钉号）
```

**依赖方向**：`api → handlers/management → config / pluginhost / watcher / access / sdk/cliproxy/auth`。**禁止** `cmd` 反向 import `internal/api` 以外的业务逻辑；删除面（tui/store/discovery/translator 大部/内置 executor）不得留"留但不导出"的僵尸匿名 import。

### 3.2 sdk/pluginabi 与 internal/pluginhost 边界

- **`sdk/pluginabi`（只放契约）**：`types.go:7 ABIVersion=1`、`:20 SchemaVersion=6`、`:36-113` method 名常量。纯数据/常量，无加载逻辑。
- **`internal/pluginhost`（放实现）**：`loader_windows.go`/`loader_unix.go`（加载）、`management.go`（路由注入）、`rpc_client.go`（method 派发）。
- **方向**：插件侧只依赖 `sdk/pluginabi`（经 `github.com/router-for-me/CLIProxyAPI/v7/sdk/pluginabi`，workbuddy/main.go:74 实测），**不反向 import host**；宿主依赖 `pluginabi` 做版本校验（`abi.go:9 pluginHostABIVersion = pluginabi.ABIVersion`，实测）。契约与实现分离、依赖单向——这是教科书式的开闭原则扩展点。

### 3.3 插件 wire/executor 边界（clean 范本）

- **`wire.go`（纯协议层）**：`workbuddy-bridge-0.1.2-source/wire.go:6-7` 自述 *"This file is pure: no C ABI, no host calls — everything here is unit-testable"*（实测）。URL/header/body 组装无 host call、可单测。
- **`executor.go`（执行层）**：SSE 逐帧清洗转发；**`plugin.go`（C ABI 胶水层）**：顶部 cgo `cliproxy_host_api`/`cliproxy_plugin_api` 结构体（:20-44）+ 四符号导出（:53-55/:89-100）。
- **启示**：cpa-multi-plugins 现状一个 .so 把 wire+签名+调度器+签到+panel 全编进去、无法按函数裁剪（`go build -buildmode=c-shared` 粒度=整插件目录）；改造时按"纯协议层 + 管理/调度层"拆分。

### 3.4 DSH 宿主半端 vs client.js

- **宿主半端 `index.js`（Node ESM，高权）**：持 adminKey（`:234 resolveAdminKey`）、spawn CPA（`:301-303`）、把 `/api/v1/cpa/*` 翻译成 CPA `/v0/management/*`（`:168 cpaFetch`）。**唯一持密钥/碰文件方**。
- **浏览器半端 `client.js`（CJS bundle，低权）**：`client.js:11` 铁律注释实测"管理密钥永远不进这一侧"；所有 fetch 同源相对路径、`credentials:'include'`、**无 Authorization 头**；只经 `/api/v1/cpa/*` 与宿主半端通信，**不直接调上游**。

### 3.5 跨仓库依赖方向（红线）

```
DSH 插件 ──(HTTP loopback, Bearer adminKey)──► CPA 宿主 ──(C ABI)──► 插件 dll ──(HTTPS)──► 上游
```
**反向一律禁止**：插件 dll 不能回调 DSH 宿主；上游不能主动进 CPA；client.js 不能碰 adminKey/文件系统。
