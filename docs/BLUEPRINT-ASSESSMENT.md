# 蓝图实施评估（S0–S7 逐阶段对照）

> 读者：决策人（拍板要不要开工、按什么顺序开工）。
> 目的：把 [蓝图·大白话版](../调研报告归档/蓝图·大白话版.md) 的每个阶段，逐条对照**当前代码事实**，
> 判定「已完成 / 需改造 / 与现状冲突 / 未验证风险」，让拍板有依据。
> 结论一句话：**蓝图的目标可以照做，蓝图的施工图不能照抄 —— 它的起跑线已过时。**

## 0. 压缩结论

| 判定 | 阶段数 | 说明 |
|---|---|---|
| ✅ 已完成（蓝图以为待做） | 3 | S0、S3 部分、S5 大部分 |

**核心事实**：蓝图写于调研阶段，作者当时认为本插件是"手写野路子、没有护栏"。
但当前 `0.1.0` 是**已发布、已实测可用**的系统，且蓝图里"能立刻带来价值"的部分**已经做完了**。
剩下的是"拆迁重建"部分，代价远大于蓝图描述。

## 2. S0–S7 逐阶段对照

阶段口径沿用 [PLAN.md §2](PLAN.md)。

### S0 准备 —— ✅ 已完成（部分被超越）

| 蓝图要求 | 现状 |
|---|---|
| 基线冻结、五仓按 SHA 取快照 | 五仓坐标与 SHA 已在 [99-入口索引](../调研报告归档/核心文档集/99-入口索引.md) 钉死 |
| 构建链验证（Go 1.26 + MinGW） | **未做** —— 这是真正缺的一环，见 S3 |

**判定**：文档侧就绪，**工具链侧未验证**。这是唯一"做了有实际价值"的准备项。

### S1 宿主瘦身 —— 🔴 与现状冲突（风险最高）

| 蓝图要求 | 评估 |
|---|---|
| 删 Docker / 自带网页 / WebRTC / Postgres / ~90 条旧接口 | 要动 **CLIProxyAPI Go 源码**（上游 fork），每删一组需 `go build` 全量回归 |
| "906 个自动测试守着，删赘肉动不到核心" | 这是**蓝图最强的论据，也是最弱的前提**：它假设执行者能跑通这 906 个测试 |

**🔴 冲突点**：当前插件**根本没用到**要删的那些模块。
删了对你**现在的使用零收益**，只有"体积更小、攻击面更小"的远期收益，
却要承担 **①改上游 fork ②维护 906 测试基线③未来无法跟上上游更新** 三项长期成本。

**建议**：**S1 整段推迟**，直到有明确的体积/安全诉求再启动。

### S2 宿主补丁 —— 🟡 拆开看，只有一半值得做

| 补丁 | 评估 | 建议 |
|---|---|---|
| 原子写 ×3（防写半截） | **真实缺陷**：写 auth JSON 中途失败会损坏凭据 | ✅ 值得做 |
| `/readyz` 就绪探针 | 现在靠端口探活 + 超时，够用但不精确 | 🟡 可选 |
| `/shutdown` 优雅停接口 | 现在走「端点 → Ctrl-C → `taskkill /F`」三级兜底，**已经能用** | 🟡 可选 |
| key→unit 捷径（方案甲） | **见 §3 —— 本评估最大的分歧点** | ⚠️ 需重新论证 |
| v0 收敛（收旧接口） | 与 S1 同性质，零当前收益 | 🔴 推迟 |

### S3 渠道插件定稿 —— 🟡 部分是**真实缺口**

| 蓝图要求 | 现状 | 判定 |
|---|---|---|
| 删 mimo | `setup.js:45` 的 `SOURCES.plugins.label` 仍写 `workbuddy / trae / qoder / zcode / mimo` | 🟡 注释与实际不符，易误导 |
| 重编 4 个 dll + SHA-256 清单 | **没有构建链**，用的都是上游 Release 现成产物 | 🔴 缺口 |
| 自编"干净版 workbuddy dll" | 蓝图自己承认"按旧版 SDK 编的，要实测能否被新主服务加载" | ⚠️ 未验证 |

**判定**：**这是蓝图里最有价值的一段**。自编 dll 是"渠道可控"的唯一路径，
但也是**唯一需要 Go + MinGW 工具链的环节**，成本真实且未知。

### S4 DSH 工程化（TS 化）—— 🟡 建议**降级执行**

| 蓝图要求 | 评估 |
|---|---|
| `index.js` → `index.ts`、`adapters.js` → `adapters.ts` | `index.js` 1498 行 + `adapters.js` 11.5 KB，`client.js` 49.6 KB |
| tsdown / vitest / ESLint / Prettier / 只读 CI | 当前**零门禁、零测试**（`dsh-cpa-switch/AGENTS.md` 自述） |

**🟡 关键判断：蓝图把"要护栏"和"改成 TS"绑成了一件事，但它们可以拆开。**

- 你要的是**护栏**（类型检查、自动测试、CI）
- 获得护栏**不必**改文件扩展名：先补 **ESLint + vitest + JSDoc 类型检查**，
  收益拿到、风险减半、不动已验证的运行时行为
- TS 化的**真实成本**被蓝图低估了：`client.js` 是**自定义 CJS 加载器 bundle**
  （`window.__ModuleLoader__.load`），不是普通 ESM —— 它有**自己的双目标构建**问题

**建议**：先补护栏（低风险），TS 化单独立项、单独立项评估。

### S5 首启与托管 —— 🟡 一半已完成，一半是真缺口

| 蓝图要求 | 现状 | 判定 |
|---|---|---|
| 首启下载/校验/写配置 | ✅ **已完成实测** | 无需做 |
| 崩溃自动重启（三级退避） | `index.js:415` 是裸 `spawn`，**无退避、无 Job Object**（全文件搜不到 backoff / JobObject） | 🔴 真缺口 |
| "插件关了就带走主服务" | `stopIfOwned()` 已实现（只在 DSH 关时关自己启的） | ✅ 基本完成 |
| `units.ts` 单元机制 | **代码里无 `unit`/`pinned` 任何痕迹** | ⚠️ 见 §3 |

### S6 UI 养号版 —— 🟡 收益不明确

蓝图要"配置页改由 DSH 宿主自动生成表单"。
**但现有 UI 是 49.6 KB 自绘面板，且渠道能力差异（F6 按能力降级渲染）正是靠自绘实现的。**
换成 schema 自动表单可能**丢失能力降级能力**。建议**不做**，除非有具体痛点。

### S7 端到端与发布 —— 🟡 有一个**明确的现实阻塞**

蓝图说"定好谁编译发布产物"。
**现状**：包已就绪（11 文件 / 42.2 KB，`check-install.mjs` 通过），
但卡在 **npm 登录**（registry 指向只读镜像 npmmirror）。

**这是唯一一个"只差一步就能落地"的项** —— 优先级应该排在所有 S 阶段之前。

## 3. 最大分歧：方案甲（每单元独立钥匙）

这是蓝图的核心创新，也是**本评估最建议重新论证的部分**。

| 维度 | 方案甲（蓝图，未做） | 现状（已做） |
|---|---|---|
| 机制 | 每单元一把 apiKey + `pinned_auth_id` 钉号 | 「选择」= 启用一个 + 禁用同渠道其余 |
| 落到哪 | **改 Go 宿主源码**（`model_execution.go` AuthID 捷径） | 只调 CPA 现成的 `disabled` 字段 |
| 用户可见结果 | 点哪个单元走哪个账号，不可用即报错 | 点哪个号用它，不可用即报错 |
| 验证状态 | **未验证**（且 G1 契约缺口未定义写端点） | **已实测 6/6 粘连通过** |

**关键观察：两者对用户承诺的「结果」是等价的 —— 都是"绝不自动换号"。**
差别在**机制硬度**与**实现代价**。

- 现状方案的硬度由 [ARCHITECTURE.md](ARCHITECTURE.md) §4.4 论证过：只有 `disabled` 是"根本不参与"，
  `priority` / `fill-first` 都会降级 —— 所以现状**已经满足"绝不偷偷顶替"**
- 方案甲要额外承担：**改上游 fork + G1 写端点未定义 + 每单元 key 注入通道未定**

**并且**：`12-实施就绪度审计报告` 自身复核后的结论是 ——
真正"实施前必须人工确认的只有 1 项 = ⑤后端小改授权"，
方案甲是"建议确认"而非"必须确认"，且注明"技术上方案乙已被否、无替代"。

**建议**：**保留现状方案，除非出现它无法满足的具体场景**（例如需要同时跑多个号且各自计费）。
在没有该场景前，改 Go 宿主是**用能跑的系统赌没验证的机制**。

> 反向证据（支持做方案甲的唯一理由）：现状的「选择」是**渠道级独占**，
> 没有"启用多个号"的入口（`AGENTS.md` 明确说这是**刻意的**）。
> 如果未来需求变成"同渠道多号并行、各自独立计费"，现状方案确实不够 ——
> 但那是**需求变更**，不是蓝图的既定前提。

## 4. 蓝图完全没提、但会翻车的坑

这些是**历史事故已经验证过**的风险，蓝图只字未提：

| 坑 | 证据 | 为什么在 S0–S7 下风险最高 |
|---|---|---|
| 路由契约：同一 path 只能注册一次、方法仅 GET/HEAD/POST | [事故记录](../../.agents/notes/incident-route-contract-2026-10-03.md)：一条抛异常 → **所有路由 404**，stderr 干净 | 加 `units` 端点必然改路由，**最容易再犯** |
| `node --check` 查不出作用域错误与契约违规 | `dsh-cpa-switch/AGENTS.md` 明写 | TS 的类型检查**也查不出运行时契约违规** |
| 删资源探测来源必须补兜底并验证冷启动 | [事故记录](../../.agents/notes/incident-exe-discovery-2026-10-03.md)：**用户服务直接中断** | S1 删模块、S3 换 dll 都是这类改动 |
| 探测脚本必须还原运行前状态 | `AGENTS.md` 活跃坑：曾把用户手动禁用的号全启用 | 新验证脚本会重犯 |
| 插件必须是 profile 下**真实目录**，不能 `link:` | [ARCHITECTURE.md](ARCHITECTURE.md) F1 | TS 化改构建产物会碰这个 |

**结论**：S0–S7 会**同时踩中全部这些坑**，而蓝图一条都没预警。

## 5. 建议的执行顺序（替代 S0–S7）

按"能带来用户可见价值 ÷ 风险"排序：

### 第一批：低风险、立刻有用（建议现在做）

1. **发布到 npm** —— 只差登录，包已就绪。解锁"别人能装"
2. **环境准备进度反馈** —— 40 MB / 96 秒黑屏，体验缺口真实
3. **修 `SOURCES` 注释**（写 mimo 但已删）+ **非 Windows 分支**
4. **补护栏**：ESLint + vitest + JSDoc 类型检查（**不改文件扩展名**）

### 第二批：中风险、有明确收益

5. **崩溃自动重启 + 退避**（S5 真缺口）
6. **限流状态显示**（`probe-usable.mjs` 已有能力，搬到面板）
7. **原子写 ×3**（S2 唯一值得做的补丁）

### 第三批：高风险、需独立论证

8. **S3 渠道 dll 自编** —— 需 Go 工具链，价值最高但成本未知，**先做工具链可行性验证**
9. **TS 化** —— 单独评估 `client.js` 的自定义 CJS bundle 如何处理
10. **S1 宿主瘦身 / 方案甲** —— 仅在有明确需求时启动
